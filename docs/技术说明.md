#### 为什么必须带 GDCM（v1.14.1）

云端 PACS 下发的 DICOM 往往**不是裸像素**。鲁云影像（ftimage 架构）给 CT 的是
**JPEG-LS 无损压缩**（`TransferSyntaxUID = 1.2.840.10008.1.2.4.80`）：

- 文件魔数、`Rows/Columns`、`WindowCenter`、`RescaleIntercept` 全部正常，看起来毫无问题；
- 但 `vtkDICOMImageReader` 只认未压缩 + JPEG baseline，遇到 JPEG-LS 会打印
  `Unable to get PixelData from ... which has TransferSyntaxUID=1.2.840.10008.1.2.4.80 (JPEG-LS)`，
  **输出 extent 正确、scalars 为空** —— 界面上就是「序列能打开，每张都是白板」；
- `pydicom` 的 `ds.pixel_array` 同样需要解码器，否则抛
  `handlers are missing required dependencies: GDCM (req. GDCM), JPEG-LS (req. pyjpegls)`。

处理方式（见 `web_bridge.py::_decompress_one`）：下载落盘后**就地解压为未压缩**
（`1.2.840.10008.1.2.1`），而不是在读取时打补丁。原因是 CT 的二维显示、MPR、
三维重建、HU 测量、AI 检测全部依赖 VTK 的体数据，只要磁盘上是未压缩的，
整条下游链路一行都不用改。

代价与边界：

| 项 | 数值 |
|---|---|
| 解压耗时 | 约 21 ms/张（512×512），419 张约 9 秒 |
| 体积变化 | 419 张 CT：54 MB → 212 MB（约 4 倍） |
| 位深保真 | `int16` 用 `view` 做**位重解释**，不能用 `astype`（会把 −1000 变成数值转换） |
| tag 保留 | `PixelSpacing` / `ImagePositionPatient` / `SliceLocation` / `Rescale*` 全部原样保留 |
| 临时目录 | 每次导入后只保留最近 3 个（`_prune_old_dirs`），否则点几次就几个 GB |

`_release_selfcheck.py` 里有 4 项专门守住它：`_decoder_ready()` 为真、
pydicom 已挂上 gdcm handler、位宽转换正确，漏打包会在发行前直接报 FAIL。

## 双模式阅片架构（v1.4.0 新增）

### 设计目标
软件的初衷是三维重建，但三维界面用于日常二维阅片效率不高。
因此引入「默认二维阅读、可手动切换三维」的双模式架构：
用户打开序列后直接进入单视图二维阅片，需要时再切到三维重建。

### 模式容器 `StudyViewPanel`

```
StudyViewPanel (QFrame)
├── 顶部模式栏
│   ├── 「二维阅读」按钮 (checkable)
│   ├── 「三维重建」按钮 (checkable)
│   └── 操作提示标签
├── Dicom2DReader      ← 始终创建
└── QuadViewer         ← 懒加载（首次切到三维时才构建三维管线）
```

- `MODE_2D = "2d"` / `MODE_3D = "3d"`，`_mode` 保存当前模式
- `mode` 为只读 property，供外部查询
- `set_mode(mode)` / `toggle_mode()` 切换模式
- `reader_2d` 为只读 property，暴露二维阅读器实例
- `mode_changed` 信号通知主窗口同步右侧工具栏

### 懒加载三维管线
三维管线构建开销大（Marching Cubes + 体渲染），因此 `QuadViewer` 不在
启动时创建，而是在首次切换到三维模式时由 `_ensure_volume()` 延迟构建：

```python
def _ensure_volume(self):
    if self._quad_viewer is None:
        self._quad_viewer = QuadViewer()
        self._quad_viewer.set_reader(self._reader, ...)
    return self._quad_viewer
```

切回二维时仅隐藏三维视图、保留已建管线，避免反复重建。

### 二维阅读器渲染管线（v1.5.0 重构）

**关键点 1：不使用 `vtkImageViewer2` 的切片逻辑**，而是自建最小管线。

**关键点 2：ImageActor 的输入必须是「单层二维 vtkImageData」**，不能把整卷
三维数据交给 ImageActor 再用 `SetDisplayExtent` 切层。

```
vtkDICOMImageReader
        │
        ▼
  numpy 视图 (nz, ny, nx[, nc])      ← vtk_to_numpy 零拷贝
        │
        │  每次换层：shape[k] → np.flipud(Y 轴翻转) → 拷入新 vtkImageData
        ▼
   vtkImageActor  (SetInputData(单层2D) + SetDisplayExtent(0,nx-1,0,ny-1,0,0))
        │
        ▼
   vtkRenderer  (正交相机 + ParallelProjection)
```

```python
def _cache_volume(self, output) -> bool:
    """序列加载时建立 numpy 视图，避免 vtkImageFlip 再复制整卷"""
    arr = vtk_to_numpy(output.GetPointData().GetScalars())
    self._volume_array = arr.reshape(nz, ny, nx)          # 单分量
    self._volume_shape = (nz, ny, nx, nc)
    self._scalar_type = int(output.GetScalarType())

def _build_slice_image(self, index):
    src = np.flipud(self._volume_array[index])            # Y 轴翻转
    image = vtkImageData()
    image.SetDimensions(nx, ny, 1)
    image.AllocateScalars(self._scalar_type, nc)
    vtk_to_numpy(image.GetPointData().GetScalars()).reshape(-1)[:] = src.reshape(-1)
    return image

def _apply_slice(self, index):
    image = self._build_slice_image(index)                # 新的数据对象
    self._image_actor.SetInputData(image)
    self._image_actor.SetDisplayExtent(0, nx - 1, 0, ny - 1, 0, 0)
```

窗宽窗位直接作用于 `vtkImageActor.GetProperty()`：

```python
self._image_actor.GetProperty().SetColorWindow(window)
self._image_actor.GetProperty().SetColorLevel(level)
```

> **为什么不用 `vtkImageViewer2`？**
> 1. 它默认把 z 轴朝向相机，与 DICOM 阅片习惯不符；
> 2. 其内部的 `vtkImageMapToWindowLevelColors` 在无输入时每次渲染都会
>    刷 `Input port 0 ... has 0 connections` 错误日志；
> 3. `vtkImageActor` 自带的 `ImageProperty` 已完成窗宽窗位映射，
>    无需再叠加一层 mapper；且映射发生在渲染时，改窗值实时生效。

> **重要（v1.5.0 修复：二维模式后续图层全黑）**
> 旧实现把整卷三维 `vtkImageData` 直接 `SetInputData` 给 ImageActor，
> 再用 `SetDisplayExtent(x0,x1,y0,y1,k,k)` 切层。实际上 OpenGL 后端会把
> 整卷当作三维纹理处理：层数较多（数百层 × 512² × 16bit ≈ 数百 MB）时
> 纹理无法完整上传，且换层并不促使纹理重建，结果是「仅开头若干层有图像、
> 之后全部黑屏」，或与载入时首张（中间层）画面完全一致地卡住。
> 修复方案：每次换层构造**全新的单层二维数据对象**交给 ImageActor，
> 纹理体量降到约 0.5 MB，必然重建。
> 实测三序列（467 / 909 / 269 层）渲染均值与 numpy 预期值相关系数 = 1.0000。

> **为什么不用 `vtkImageFlip` 了？**
> 原先 `vtkImageFlip` 会把整卷再复制一份（数百层时额外占用数百 MB）。
> 现在直接从 numpy 视图取层并用 `np.flipud` 完成同样的 Y 轴翻转，
> 零额外内存，且 `_build_thumbnails()` 复用同一份视图。

#### 相机适配
```python
def _fit_camera(self):
    renderer = self._renderer
    camera = renderer.GetActiveCamera()
    camera.ParallelProjectionOn()
    camera.SetViewUp(0, -1, 0)   # 翻转后 Y 向下为图像上方
    # ResetCamera 会沿用相机当前的视线方向，只重算距离；
    # 先强制一个确定方向（+Z 侧），保证下面的镜像是幂等的
    camera.SetFocalPoint(0.0, 0.0, 0.0)
    camera.SetPosition(0.0, 0.0, 1.0)
    camera.SetViewUp(0, -1, 0)
    renderer.ResetCamera()
    renderer.ResetCameraClippingRange()
    # 此时相机必然在 +Z 侧，镜像到 -Z 侧与三维视图一致
    pos = camera.GetPosition(); fp = camera.GetFocalPoint()
    camera.SetPosition(pos[0], pos[1], fp[2] - (pos[2] - fp[2]))
    renderer.ResetCameraClippingRange()
    camera.Zoom(1.15)
```

单层图像的 z=0 恒定，因此相机只需在加载时适配一次，换层不会导致裁剪错位。

### 观察方向必须与 MPR 一致（v1.5.1 修复：二维画面左右反转）

同一批数据（都做过 Y 轴翻转）、同一个 `ViewUp = (0,-1,0)`，
但**相机放在 Z 轴的哪一侧**决定了画面的左右：

| 相机位置 | ViewPlaneNormal | ViewRight = up × normal | 屏幕右方向 |
|---|---|---|---|
| +Z 侧（错误） | (0,0,+1) | **(-1,0,0)** | 世界 **-X** |
| -Z 侧（`vtkImageViewer2`） | (0,0,-1) | **(+1,0,0)** | 世界 **+X** |

`vtkImageViewer2` 的 XY 方向相机位置为 `(0,0,-1)`，即**位于 -Z 一侧**。
二维阅读器原先自建相机，`ResetCamera()` 默认把它放在 **+Z 一侧**，
于是屏幕图像 = 原图左右翻转（`fliplr`），表现为「二维左右反、三维正常」。

解析验证（取第 k 层，数据已 Y 翻转）：
- 相机 -Z 侧：屏幕 `row r, col c` → 数据点 `(i=c, j=ny-1-r)` → 原图 `(c, r)`，即**原图**
- 相机 +Z 侧：屏幕 `col c` → `i=nx-1-c`，即 **`fliplr(原图)`**

同时该方向也符合放射学阅片惯例：`ImageOrientationPatient = [1,0,0,0,1,0]`
表示列索引 i 增大方向 = LPS +X = 患者 **Left**；轴位从足侧观察时
**患者左侧显示在图像右侧**，即屏幕右 = i 增大 = +X —— 与 -Z 侧相机一致，
也与画面左侧标注的「右」字吻合。

> **坑：`ResetCamera()` 会沿用当前视线方向。**
> 若只做「把相机镜像到 -Z 侧」，第一次加载正确、第二次加载时相机已在 -Z 侧，
> 再镜像一次就翻回 +Z。必须先把相机强制回 `(0,0,1) → (0,0,0)` 方向再镜像。

### 序列默认窗宽窗位（v1.5.0 新增）

`analyze_dicom_series()` 已经解析出 DICOM 的 `WindowCenter` / `WindowWidth`，
但旧代码在加载完成时把它丢弃，硬编码为 `1500 / 300`，导致部分序列一打开就是黑屏。

```python
def _plausible_window(window, level) -> bool:
    """设备写入的 DICOM 窗值可直接用于显示"""
    return 1.0 <= w <= 6000.0 and -1500.0 <= c <= 1500.0

# 加载完成回调
if self._plausible_window(window_width, window_center):
    window_width, window_center = float(window_width), float(window_center)
else:
    window_width, window_center = self._fallback_window_level(is_lung)
```

优先级：**序列自身窗值 > 部位兜底（肺窗 1500/-600，其余 400/40）**。
DICOM 缺省或数值离谱时才走兜底。

#### 键盘事件捕获
VTK 的 interactor 只在拥有焦点时收到按键，且 Qt 事件先到 QWidget。
因此在 `Dicom2DReader` 上对 VTK 控件安装 `eventFilter`，在 Qt 层统一处理：

```python
self._vtk_widget.installEventFilter(self)

def eventFilter(self, obj, event):
    if obj is self._vtk_widget and event.type() == QtCore.QEvent.KeyPress:
        if self._handle_slice_key(event.key()):
            return True          # 已消费，不再传给 VTK interactor
    return super().eventFilter(obj, event)
```

同时在鼠标按下时 `self._vtk_widget.setFocus()`，保证点击画面后键盘立即生效；
`keyPressEvent` 作为兜底路径复用同一个 `_handle_slice_key()`，不会重复触发。

### 缩略图条 `ThumbnailStrip`
- 直接从 numpy 体数据视图取层生成灰度缩略图（`_extract_slice` + `np.flipud`）
- 超过 200 层时按比例采样（`THUMB_SAMPLE_LIMIT = 200`）
- 生成动作由 `QTimer.singleShot` 投递到主线程，避免在 VTK 渲染回调中重入
- 点击缩略图发出 `slice_requested` 信号，由阅读器跳转到对应层

### 序列文件过滤（重要）
`vtkDICOMImageReader.SetDirectoryName()` 会**无差别扫描目录内所有文件**。
若目录中存在非 DICOM 文件（如设备生成的 `ko`、`*.xml`），
`vtkDICOMImageReader` 可能直接**原生崩溃（段错误）**，而非抛出异常。

因此 `DicomLoadWorker` 在调用读取器**之前**先做暂存过滤：

```python
def run(self):
    # 1. 先暂存有效 DICOM 文件（同时供分析器与读取器使用）
    folder, temp_folder, copied_count = self._copy_selected_files(
        folder, self._file_uids)
    # 2. 再在干净目录上执行元数据分析
    params = self._analyzer_fn(folder)
    # 3. 最后交给 vtkDICOMImageReader
    reader.SetDirectoryName(folder)
```

`_stage_valid_dicom()` 的有效性判定：
1. 文件偏移 128 处是否为 `DICM` 魔数；
2. `pydicom.dcmread(..., force=True)` 能否解析；
3. 无需要剔除的文件时直接复用原目录，避免多余拷贝。

### 取图策略（只读 1~3 个文件）

预览图**不加载整个序列**，只挑序列中段的候选层：

```python
def _preview_candidate_paths(folder, file_uids, count=3):
```

### 并发模型（踩坑记录）

最初用 `QThreadPool + QRunnable`，把 `pyqtSignal` 挂在 QRunnable 上，
**回调全部丢失**（`_thumb_pending` 35 个、回调 0 个）。原因：
`QRunnable` 默认 `setAutoDelete(True)`，`run()` 返回后对象被析构；
PyQt 只在信号**被 emit 的时刻**才建立连接，排队期间连接尚不存在，
因此 emit 落空。把信号对象改为由主窗口持有后，在独立小脚本里可以
收到回调，但在 `MainWindow` 完整初始化路径下仍然全部丢失。

最终改用 **`QThread` 子类 + 队列轮询**（`SeriesThumbnailWorker`）：
队列由主线程 `append`（GIL 保证原子），线程侧轮询消费，单张约 30ms，
轮询开销可忽略。`QThread` 子类自带信号，回调稳定可靠 —— 实测
**35 请求 / 35 回调**全部送达。

## 序列张数精确化（v1.6.1 修复）

### 症状
同一检查的肺窗 / 纵隔窗（或骨窗 / 脑窗）薄层本应张数一致，
列表里却显示成不同数字（实测 `1.0 x 1.0` 一对被显示成 463 与 362）。

### 根因
`_analyze_series_from_dicom_fast()` 用**采样估算**张数：

```python
# 旧实现（已废弃）
sample = 最多 30 个文件                    # 识别有哪些 SeriesInstanceUID
files_per_series = max(5, 30 // len(series_groups))
check_indices = range(0, total_files, max(1, total_files // files_per_series))
count = 命中该 UID 的采样文件数
series_groups[uid]['count'] = int(count * ratio)   # ratio = total / len(check_indices)
```

一个目录里往往交错存放多个序列（薄层骨窗 / 标准窗交替写入），
**用 5~30 个样本去推 1500 个文件的分布，比例必然失真**，
且不同 UID 的失真方向不同 → 成对序列被算成完全不同的张数。

### 修复：目录级精确索引

新增 `_scan_folder_series_index(folder)`：一次性扫描目录内**全部** `.dcm`，
按 `SeriesInstanceUID` 精确分组计数，结果按目录缓存（指纹 = 文件数 + 最大 mtime）。

为了让全量扫描不至于变慢，新增 `_read_series_uid_fast()`：
绝大多数 CT 是 Explicit VR Little Endian，直接在文件头 8KB 内
按 `(0020,000E)` + `UI` 定位 `SeriesInstanceUID`，命中即返回，
不再构造 Dataset；未命中（隐式 VR 等）才回退 `pydicom.dcmread`。

| 目录 | 文件数 | pydicom 全量 | 快速字节扫描 |
|---|---|---|---|
| ...8202604201 | 1599 | 3.3s | **0.79s** |

抽查 40 个文件，快速读取结果与 `pydicom` **0 个不一致**。
`collect_ct_patients` 冷缓存总耗时 4.6s（改动前 5.5s），热缓存 1.5s ——
精确化之后反而更快（原先的两次采样共读 60 个文件，开销并不低）。

### 顺带修复：XFD 序列加载了整个目录

`_parse_xfd_sequences()` 收集的 `sopuids` 是 **SOPInstanceUID**，
而 `_load_series` 约定 `file_uids` 是「文件名去掉 `.dcm`」，
两者永远匹配不上 → `DicomLoadWorker._copy_selected_files` 拷贝数为 0 →
退化为 `_stage_valid_dicom()` 暂存**整个目录** →
`vtkDICOMImageReader` 把目录内所有序列读成一个体数据。

现在改用按 UID 精确扫描出的文件名清单（按名排序），
实测某目录从「加载全部 289 张（含多个序列混合）」变为「只加载目标序列 229 张」，
列表张数与实际层数一致。

XML 分支同样处理：仅当既有清单解析出的文件数少于精确张数时才替换，
清单本身完整时保持不动，避免改变原有的层序。

### 患者行点击行为（v1.6.1 调整）

原先双击患者姓名会自动加载第一个序列，几百层数据要等数秒才有反应，
而用户此时往往只是想浏览有哪些序列。改为：

| 操作 | 行为 |
|---|---|
| 单击患者行 | 切换展开/收起，展开即呈现序列缩略图，**不加载** |
| 双击患者行 | 仅展开（不再自动加载） |
| 双击序列卡片 | 加载该序列（原行为不变） |

配套开关：

```python
self._patient_tree.setExpandsOnDoubleClick(False)   # 关掉双击自动展开
self._patient_tree.itemClicked.connect(self._on_tree_item_clicked)
self._patient_tree.itemExpanded.connect(self._on_patient_expanded)
```

由于 Qt 在双击时也会连续发出两次 `itemClicked`，
`_on_tree_item_clicked()` 用 `QTime` 比对 `QApplication.doubleClickInterval()`
吃掉第二次点击，否则会出现「展开→收起」闪动。

### 元数据合理性校验
部分设备（尤其是 Scout 定位像）会写入明显失真的元数据。
叠加层展示前做量程校验，超范围则显示 `-`：

```python

    return 0.1 <= float(value) <= 20.0

@staticmethod

    return 0.05 <= float(px) <= 5.0 and 0.05 <= float(py) <= 5.0
```

- 依赖库：numpy, scipy
- 操作方式：在MPR视图中右键点击添加中心线点
- 最少点数：3个点生成曲面
- 视觉反馈：
  - 绿色球体标记中心线点（在MPR视图中实时显示）
  - 青色线条显示中心线路径（在3D视图中显示）
- 实现原理：
  1. 在MPR视图中采集中心线点（右键点击）
  2. 沿血管中心线进行插值
  3. 计算中心线的切向量和垂直向量
  4. 沿垂直方向采样生成CPR图像
  5. 在新窗口中显示CPR结果
- 图像显示：
  - 数据类型转换为int16
  - 归一化到CT值范围（-1000到3000 HU）
  - 使用vtkImageViewer2显示

#### CPR算法流程
```python
# 1. 提取体数据
volume_data = vtk_to_numpy(vtk_array).reshape(dims)

# 2. 创建3D插值器
interpolator = RegularGridInterpolator((z_coords, y_coords, x_coords), volume_data)

# 3. 计算中心线弧长参数
arc_length = cumsum(sqrt(sum(diff(points)^2, axis=1)))

# 4. 生成密集中心线点
centerline_points = interpolate(sample_arc_lengths, arc_length, points)

# 5. 计算垂直于中心线的基向量
tangents = gradient(centerline_points)
perpendicular1 = cross(tangents, ref_vector)
perpendicular2 = cross(tangents, perpendicular1)

# 6. 沿中心线采样生成CPR图像
for each point on centerline:
    for each offset in width_coords:
        sample_point = center_point + offset * perpendicular
        cpr_image[i, j] = interpolator(sample_point)
```

## 二维测量工具（v1.6.2 新增）

二维模式（`Dicom2DReader`）新增三种测量工具，工具栏位于视图区左下角、
「全屏 / 序列」按钮右侧，包含 **CT值 / 长度 / 角度**（三者互斥）与 **清除** 按钮：

| 工具 | 操作 | 结果 |
|------|------|------|
| CT值 | 单击图像放置圆心 | 以该点为中心画一个圆形 ROI，显示**区域内平均 HU**（及半径 mm、像素数 n）；光标移动时浮标实时跟随单点读数 |
| 长度 | 依次单击两点 | 两点间直线距离（mm），中点处标注 `xx.x mm` |
| 角度 | 依次单击三点（射线端—顶点—射线端） | 顶点处夹角（度），标注 `xx.xdeg` |
| 清除 | 点击 | 移除当前序列全部测量标记 |

**CT 值的圆形 ROI 半径调整**（点测量已改为区域平均，避免单像素噪声）：
- 滚轮（CT 工具激活时、未按 Ctrl / 中键）：**向前放大、向后缩小**圆形 ROI 半径。
- 键盘 `[` / `]`：同样缩小 / 放大半径（增量 1.1 倍）。
- 半径范围 0.5–100 mm，调整后已放置的 ROI 会**自动重算平均 HU**。
- 半径仅占用 CT 工具的滚轮；**翻层仍可用右侧滑条**，Ctrl+滚轮 / 中键拖动仍缩放平移。

### 设计要点

1. **测量结果按层存储**：每条测量记录绑定 `slice`（当前层索引），切层后只绘制
   属于该层的标记；加载新序列或点击「清除」会整体重置。
2. **坐标统一用世界坐标存储**：所有端点以 VTK 世界坐标保存，绘制时再换算到屏幕，
   因此平移 / 缩放 / 调窗后测量图形始终跟随解剖结构，不会错位。
3. **屏幕↔世界换算**：用 `vtkRenderer.WorldToDisplay()` / `DisplayToWorld()` 互转，
   已用真实窗口验证往返误差 ≈ 1e-14，且正交投影下 X/Y 与深度无关（鼠标事件
   直接传 z=0 即可）。屏幕像素→Qt 控件坐标再按 `renderer.GetSize()` 与渲染区尺寸比例修正，
   兼容高 DPI。
4. **CT 值（HU）直接取自体数据**：本项目二维体数据来自 `vtkDICOMImageReader`，
   该读取器在**读取阶段已经应用了 Modality LUT（RescaleSlope / RescaleIntercept）**，
   因此 `_volume_array` 中保存的**已经是 HU 值**。`_ct_value_at()` / `_ct_mean_in_circle()`
   直接取用即可，**绝不能再乘一遍 slope / intercept**——否则会把骨密度
   （+1000HU 左右）算成 `1000 + (-1024) = -24` 之类的负数（这正是 v1.6.2 后期
   「测骨头出负数」的根因，已修复）。`_build_dicom_info()` 仍读出 rescale 系数，
   但仅作记录/诊断用途。Y 轴在构造单层图像时做了 `np.flipud`，采样时先翻回原始
   行号再取值，保证取到的是屏幕上看到的那一像素。
   **圆形 ROI 平均值**（`_ct_mean_in_circle`）：以圆心 + 半径（mm）在世界坐标下圈定
   真圆（各向异性 spacing 下仍是解剖学真圆），逐行按 X 方向圆内区间剪枝遍历，
   直接累加 HU 后求均值；同时给出 min / max / 像素数。半径较大时只遍历圆内像素，性能可控。
5. **长度 / 角度单位即 mm**：图像 spacing 以 mm 为单位，世界坐标距离就是物理距离，
   无需再乘像素间距；角度在世界坐标平面直接用矢量点积求夹角。
6. **与原有交互互不干扰**：左键不再用于平移（用户不需要左键平移，已移除）；
   测量工具激活时左键用于下点；右键调窗、中键 / Ctrl+滚轮 平移缩放仍然可用；
   按 `Esc` 取消正在进行的测量（长度 / 角度的草稿点）。
7. **绘制（VTK overlay 叠加层）**：测量图形一律画在渲染窗口的**第二层
   `overlay_renderer`（Layer 1，与图像共享同一相机）** 中——线 / 点用世界坐标
   （随图像平移缩放自动跟随），文字与 CT 十字用显示坐标（恒定屏幕大小）。
   这样做的原因是：**Qt 子控件无法正确覆盖在 VTK 的 OpenGL 原生窗口之上**
   （透明子控件透出的是父窗体背景而非 GL 图像，会整片黑屏），所以测量必须
   作为 VTK actor 画在 GL 上下文内。数值与线段颜色：长度 / 角度为青色
   （`#00E5FF`），CT 探针为黄色（`#FFD54F`），文字带半透明黑底气泡。
   注意 VTK 默认字体仅支持 ASCII，角度单位用 `deg` 而非 `°`。

### 关键代码位置（`main.py`）

- `Dicom2DReader.__init__()`：创建 `overlay_renderer`（Layer 1，共享相机）
- `Dicom2DReader._build_measure_toolbar()` / `_init_measure_state()`：工具栏与状态
- `Dicom2DReader._on_measure_click()` / `_on_measure_hover()`：鼠标交互
- `Dicom2DReader._ct_value_at()` / `_seg_mm()` / `_angle_deg()`：数值计算
- `Dicom2DReader._world_to_display()` / `_display_to_world()`：坐标换算
- `Dicom2DReader._rebuild_measure_actors()` 及 `_mk_world_line_actor()` /
  `_mk_disp_line_actor()` / `_mk_text_actor()` / `_add_ct_marker()`：绘制
- `MainWindow._build_dicom_info()`：新增 `rescale_slope` / `rescale_intercept`

### 验证

合成体数据 + 真实窗口端到端测试：坐标往返误差 ≤ 1e-14；CT 值取
`_volume_array` 中已由 VTK 应用过 Modality LUT 的 HU（不再二次换算，避免骨密度变负）；
长度 10.0 mm、角度 90.0° 数值正确；绘制路径无异常；工具栏按钮齐备；
测量模式切换后平移 / 缩放仍可用。

## X 线辅助诊断集成（v1.7.0 新增）

### 目标与结论

把独立的「X 线辅助诊断系统」（`xray/` 目录，自带嵌入式 Python 与 12 个 ONNX 模型）
并入 CT3D：**患者列表共用、CT 与 DR 同列表展示、X 线仅二维、AI 按钮置于最右侧工具栏**。

**实测结论（决定了整体方案）**：CT3D 自带的 `pyenv`（Python 3.8.3）可以直接 import
并运行 xray 的全部推理模块——onnxruntime 1.19.2 / opencv 4.12 / numpy 1.24 均已齐备，
9/9 模块导入成功，胸片推理 0.1s、脊柱推理 2.5s。因此采用**进程内模块级集成**，
不需要第二个 Python 环境，也不需要拉起 xray 的 exe。

### 包名冲突：utils.py → ct3d_utils.py

xray 的 `app/` 根下有 `utils/` 包，CT3D 根目录原本是 `utils.py`。`sys.modules`
里同一个名字只能存在一个，且 CT3D 代码执行 `from utils.logger import ...`（xray 侧）
时会因 CT3D 的 `utils` 是模块而非包而失败。

改名成本对比：xray 侧有 **21 处** `from utils.xxx import` 引用（16 个文件），
CT3D 侧只有 **1 处**（`main.py` 的 import 行）。因此把 CT3D 的 `utils.py`
改名为 **`ct3d_utils.py`**，xray 侧保持原样。

### X 线进入患者列表的四道关卡

原本 X 线数据处理不到，依次被四处拦掉，全部已放开：

| # | 位置 | 原逻辑 | 现逻辑 |
|---|---|---|---|
| 1 | `_iter_patient_dirs` | 只认目录名以 `ct` 结尾 | 增加 `_dx/_cr/_dr/_rf/_xa/_mg` 后缀 |
| 2 | `_parse_xfd_sequences` | 只认 CT 的两个 Storage Class UID | 增加 `XR_CLASS_UIDS`（DX/CR/MG/XA/RF），并记录每序列的模态 |
| 3 | `collect_ct_patients` | `if modality != "CT": continue` | 放宽为 `CT` + `is_xr_modality()` |
| 4 | `collect_ct_patients` | `if img_count <= 1: continue`（当作报告页丢弃） | X 线一张片子就是一个序列，1 张是常态，**不再丢弃** |

补充：部分设备不生成 XFD，此时退化为「按 SeriesInstanceUID 直接扫目录」；
患者姓名改为优先读 DICOM 头（`_read_patient_info_from_dicom`），否则会退化成
目录名（如 `DX53650_DX`）。

**GBK 中文修复**：国产设备把中文按 GBK 写入 DICOM，pydicom 默认按 Latin-1 解出
`'Ñü×µÕýÎ»'` 这类乱码。新增 `_fix_gbk_text()`（`latin-1` 编码回字节再按 `gbk` 解码），
用于 `SeriesDescription` / `BodyPartExamined` / `PatientName`。修复后
`'Ñü×µÕýÎ»'` → `腰椎正位`。

### 单帧影像被拒：DicomLoadWorker 的 Z 维校验

`DicomLoadWorker.run()` 原有一句

```python
if extent[1]-extent[0] <= 0 or extent[3]-extent[2] <= 0 or extent[5]-extent[4] <= 0:
    raise RuntimeError("DICOM数据维度异常")
```

对 CT 是合理的（体数据至少两层），但 **X 线单帧影像 Z 维必然为 1**，会稳定抛
「DICOM数据维度异常」。新增 `allow_single_slice` 参数，仅 Z 维的校验按模态放宽。
`Dicom2DReader` 本身用 `nz=1` 的数据完全正常（`slice_range()` 返回 `(0,0)`）。

### 窗宽窗位：X 线量纲与 CT 不可比

两处 CT 专用校验会破坏 X 线显示：

1. `MainWindow._plausible_window` 要求 `WW ∈ [1,6000]`、`WL ∈ [-1500,1500]`。
   实测 X 线 DICOM 写的是 `WW=7170 / WL=12798`，被判为不合理 → 兜底成 `400/40` → **整幅发黑**。
2. `Dicom2DReader.set_window_level` 的 `_safe()` 用同样的区间钳制，
   即便上游算对了（实测 `WW=7005 / WL=12880`）也会被**再压回 400/40**。

处理：X 线改用 `MainWindow._xr_window_level()` 按**像素分布**（1%~99% 分位）推算
显示区间，并把 `set_window_level` 的钳制上限放宽到 16bit 量纲
（`WW ≤ 100000`、`|WL| ≤ 40000`）。CT 侧的越界值已由 `_plausible_window`
在上游拦掉，放宽不影响 CT。

### 标注图显示：行序差异导致的上下镜像

xray 各模块返回的 `result_image` 已经画好了中文标签、Cobb 角弧线、骨龄关节标注，
因此**整幅替换**是还原度最高也最省事的做法——在 `Dicom2DReader` 里新增一个
专用 `_ai_actor`（与 `_image_actor` 共用同一相机与 spacing/origin，靠可见性切换）。

**坑**：不要照抄 `_build_slice_image` 的 `np.flipud`。两者的输入行序相反：

- `_build_slice_image` 的输入是 `vtkDICOMImageReader` 的输出，行序为「下→上」；
- xray 的 `result_image` 来自 pydicom/cv2，行序为「上→下」（与磁盘 DICOM 像素顺序一致）。

若再 `flipud` 一次就会上下镜像（已实测复现并修正）。
同理，**不要再把二维视图里的 ndarray 喂给 xray**（曾打算给胸片/足弓省一次读盘），
两份数组行序相反，标注一定会错位；五个功能统一走「文件路径」接口。

### 灰度极性：MONOCHROME1 是负片，必须反相（v1.7.1 修复）

国产 DR 设备（实测颈椎/腰椎正位）把片子按 `PhotometricInterpretation = MONOCHROME1`
存档，按 DICOM 标准该标记表示**像素值越大越暗**，即文件里存的本就是负片。

`vtkDICOMImageReader` **完全不处理** PhotometricInterpretation，把原始灰度直接送进
渲染管线，于是 CT3D 二维视图显示 DR 时整幅是负片（骨头暗、背景白）。

判定用的是本项目惯用的相关系数法：把渲染结果与两套预测图（xray 侧正确渲染 /
其负片）比对，得到 **-0.9998**，即与「正确极性」严格反相——说明不是对比度问题，
而是极性反了。

修复分两处（两处必须用同一套换算，否则窗值与数据不同域）：

1. **显示侧**（`main.py`）
   - `series_needs_invert(reader, modality)`：X 线且 `MONOCHROME1` 时返回 True；
   - `Dicom2DReader._invert_polarity()`：`x' = (min + max) - x`，对**区间中点**镜像
     而不是简单 `max - x`，保证映射前后取值范围一致；
   - `_build_slice_image()` 与 `_build_thumbnails()` 在取层后套用（缩略图与主视图
     必须同极性）；
   - `MainWindow._xr_window_level(reader, invert=True)` 同步把 1%~99% 分位区间镜像，
     且镜像基准 `arr.min()+arr.max()` 必须取**整幅**——用抽样 min/max 会在抽样漏掉
     极值时整体偏移，导致画面一端被裁。
   - CT 恒为 `MONOCHROME2`，`series_needs_invert` 直接返回 False，零影响。

2. **AI 输入侧**（`xray_bridge.py`）
   xray 的**骨折 / 脊柱 / 骨龄**三个引擎走 `.dcm` 分支时只裁窗、不反相
   （`fracture_inference._load_image`、`spine_inference._load_image`、
   `boneage_inference._load_image`），实测它们的 `result_image` 与正确渲染的相关系数
   都是 **-1.0000**（严格取反）。这会同时污染两件事：模型吃进去的是负片、画出来
   的标注图是负片。
   处理放在**入口**而不是事后反相结果图——事后反相会把检测框/中文标签的颜色一起
   翻转（红变青）。`corrected_source()` 把负片按正确极性渲染成一张临时 8bit 灰度图
   （`load_image_rgb` 已做 MONOCHROME1 反相）交给引擎，用完即删；非负片（MONOCHROME2）
   原样走原路径。该引擎的 `.dcm` 分支本来就是「裁窗 → 归一化 uint8」，换 8bit 图
   不损失可用精度。

   实测反相前后检测结果会变（`D:\Cache\1\20260204` 三张颈椎正位）：
   脊柱 Cobb 角从「2 张可测、1 张测不出」变为 **三张全部可测**（19.6° / 19.0° / 7.4°）；
   骨折从「1 张 1 处 / 1 张 2 处」变为 **三张均为未检出**。
   判断依据：xray 自己的初始显示走 `preprocessor.load_image`（正确极性），
   而 `predict_fracture.py` 的非 DICOM 分支同样走正常极性的图片，
   说明模型是按正常极性的 X 线训练/验证的，喂负片属实现缺陷。

`MainWindow._apply_modality_ui(is_xray)` 统一处理：

### 检测记录：原库 2.96 GB 的成因与处理

xray 的 `detection_records.db` 原本 **2.96 GB**（仅 99 条记录）。原因是
`make_json_serializable()` 把整张 `result_image` 也序列化进 `results_json`
（实测 avg 20.6 MB/条，max 62 MB）。

处理：

- 新记录**只存文本摘要与关键指标**，不再写图像（`DetectionRecordStore.add`）；
- 列表查询做**列裁剪**（不 SELECT `results_json`）。SQLite 不读未选中的大字段，
  因此即使库里还留着历史大字段，99 条记录的列表查询仍只需 **0.17s**；
- 提供「清理历史图像数据」按钮：备份为 `.bak` 后重建表并 `VACUUM`，
  只丢弃图像、保留全部记录信息。**这是用户显式确认才会执行的操作**，
  不自动改动用户既有数据。

### 线程与清理

沿用 CT3D 既有约定（QThread 子类，不用 QRunnable）：`XrayAIWorker` 输出归一化结果
`dict`，模型**按需懒加载**（五个模型合计约 300 MB，全部预加载会拖慢启动）。
`closeEvent` 中新增该线程的 `stop()` + `wait(3000)`。

### AI 功能的部位适用性约束（v1.9.1 新增）

**问题**：五个 AI 功能各自只在特定部位上有意义，但界面上一直是「载入 X 线就
全部放开」。在胸片上点「足弓测量」，模型照样跑完并给出一个角度值 ——
数值毫无临床意义，却与正常结果长得一模一样，**比直接报错更危险**。
骨龄模型喂胸片同理（会输出一个「骨龄 X 岁」）。

**方案**：把「部位 → 可用功能」显式定义成一张表（`ct3d_utils.XRAY_AI_PART_SCOPE`），
载入 X 线时先判检查部位，再按表放开按钮；点击路径上再拦一次。

| 功能 | 适用部位 |
|---|---|
| 胸片检测 | 胸部 |
| 骨折检测 | 四肢/关节、手腕、脊柱、足部（**不含胸部**：胸部有专门检测，且肋骨骨折不在该模型训练范围内） |
| 脊柱侧弯 | 脊柱 |
| 骨龄评估 | 手腕（RUS-CHN 的拍摄规范就是左手腕正位） |
| 足弓测量 | 足部 |

**部位判定分三层**（`MainWindow._xray_refresh_part()`），逐层降级：

1. `xray_part_key_from_dicom(path)`：读 DICOM 头的 `BodyPartExamined`、
   `SeriesDescription`、`StudyDescription`、`ProtocolName`，先过 `_fix_gbk_text`
   修国产设备 GBK 乱码，再按关键词表匹配；
2. 列表里已有的 `body_part` / `series_description` 字段（不重复读盘）；
3. xray 侧 `BodyPartDetector.detect_from_dicom()` 的粗分类
   （`chest_xray` / `fracture` / `spine` / `bone_age`）映射成细分部位。

**关键词表的顺序即优先级**，两条必须守住：

- 足 / 腕排最前（最特异，命中即锁定功能）；
- **脊柱必须排在胸部之前** —— 「胸椎」「胸腰段」都含「胸」字，先判胸部会把
  腰椎正位误判成胸片（实测数据里 `腰椎正位` 就是这么被吃掉的）；
- 四肢放最后兜底（它是泛称，不该抢走更特异的部位）。

**UI 行为**：

- 不适用的按钮置灰，tooltip 追加「⚠ 当前片子的检查部位是「胸部」，足弓测量 不适用于该部位。」；
- 分组顶部写明「当前部位：胸部，可用：胸片检测」；
- 「智能识别并检测」在判不出部位时**不自动执行**（`XRAY_AUTO_PICK` 查不到就提示
  手动选），避免用错模型给出无意义结果；
- 部位判不出或识别失败时**全部放开** —— 设备乱写/不写 `BodyPartExamined` 是常态，
  不能因为判不出就锁死功能，改用提示文案提醒用户自行判断。

**显式出口**：「检测设置」里新增「忽略部位匹配限制（不推荐）」复选框，
写入 xray 的 `detection_settings.json`（键 `ignore_part_scope`，默认 False），
保存后立即重算按钮状态。用于设备字段写错、导致本该可用的功能被置灰的情况。

**验收**：判定层 `_test_xray_part_scope.py`（58 项，含 GBK 乱码部位、文件级兜底、
表完整性）；UI 层在 `_test_xray_integration.py` 的 K 组（15 项，直接在真实 MainWindow
上断言按钮可用性 + 点击拦截 + 弹窗文案）。

### 儿童胸片的心影校正（v1.9.3 新增）

**问题**：胸片检测在儿童片上**几乎必报「心脏肥大」**，置信度还极高（实测
0.77~0.86，比成人真阳性还高）。这不是模型坏了 —— 婴幼儿心影在胸片上本来
就相对大，心胸比（CTR ＝ 心脏最大横径 / 胸廓横径）的正常值随年龄变化：

| 年龄 | CTR 生理上限 |
|---|---|
| < 1 岁 | 0.60 |
| 1 ~ 4 岁 | 0.55 |
| ≥ 5 岁 | 0.50（与成人同） |

而 VinDr-CXR 这个模型是拿成人数据训的，成人 0.50 那条线套在孩子身上必然误报。
实测本机的 X 线库里 37 个序列，**5 张胸部片全部是 2~6 岁的儿童片，一张成人
胸片都没有** —— 所以用户的体验就是「每次胸片检测都说心脏肥大」。

**方案**：不做「一刀切屏蔽」，而是按年龄做**二次判读**。读患者年龄，对
Cardiomegaly 这一个类别，用模型给出的心脏框估算 CTR，与该年龄的生理上限
比较，只有超出上限才作为病变报出。其余 13 类完全不受影响。

#### 判定规则（`ct3d_utils.review_cardiomegaly`）

| 情形 | 处理 |
|---|---|
| 年龄未知 / 年龄格式异常 | **不校正，保留**（宁可多报，不能因为读不到年龄就把功能锁死） |
| 成人（≥ 15 岁） | **不校正，保留** |
| 儿童 + CTR 可估，超出上限 + 0.01 | 保留为阳性，注明估计 CTR 与该年龄上限 |
| 儿童 + CTR 可估，未超出 | 降级为**「心影偏大（儿童生理性）」**，灰框，不计入检出病变数 |
| 儿童 + CTR 不可估 | 降级为**「心影偏大（未能核实）」**，暗黄框，不计入检出病变数 |

最后一行是踩过坑才改的：最初写的是「拉高儿童置信度门槛兜底」（0.25 → 0.55），
**实测完全无效** —— 真实儿童片上该模型的置信度普遍 0.77~0.86，门槛提到 0.8
都拦不住任何一张。与其装样子，不如诚实标为「未能核实」，把原始结论和置信度
一并交给用户判断。CTR 判定另加了 **0.01 容差**：估算本身有 ±0.03 量级误差，
恰好卡在阈值上（例如 8 岁估出 0.502）不该判异常。

#### 年龄从哪来（`patient_age_years`）

优先 `PatientAge`（AS 类型：`005Y` / `018M` / `030D` / `002W`，也容忍设备直接
写 `12`），退回 `PatientBirthDate` + `StudyDate` / `SeriesDate` / `AcquisitionDate`
自己按月折算。只读头不读像素。**实测本机 X 线库 37/37 都能解出年龄**，
所以没有再加人工输入入口。

#### 胸廓横径估算（`estimate_thorax_width`）—— 这里改了三次

这是本次最费劲的一处，前两版都被真实数据打回：

1. **v1**：「跳过黑边 → 找胸壁亮带 → 找进入肺野的下降沿」三段结构。
   在合成图上误差 < 0.5%，但真实片子上**完全失效** —— 阳性列剖面从边界进到
   胸腔后一路维持高位，中间从不回落到阈值以下（胸腔里不止肺野，脊柱、纵隔、
   肋骨、膈下腹部的密度叠在一起）。实测 5 张真实儿童胸片 **4 张算出负值或算不出**。
2. **v2**：改用「列均值剖面的 1% / 55% 分位数定两个平台，取最长连续曝光段」。
   真实片全部通过，但合成图暴露出致命脆弱点：**心脏框很宽时（占列宽近一半），
   55% 分位会被心影亮度拉高**，阈值随之上移、肺野被当成背景剔掉，胸廓被低估
   一半、CTR 虚高到 1.0 —— 正是最不该错的方向（会误报）。
3. **v3（现行）**：中心平台取**中间 40% 列的均值**（胸腔中部必是曝光区，
   不会被边缘结构带偏），边缘平台取**最外侧 3% 列的中位数**，两侧各算各的
   阈值；某侧若没有黑边（片子已裁到皮肤），高差不足就直接从该侧边缘起算。

**精度口径必须说清楚**：这样测到的是**胸廓外缘（含软组织）**宽度，比 CTR
定义里的「肋骨内缘」约宽 5%~15%，因此算出的 CTR **系统性偏低**。这是有意保留
的 —— 宁可漏报一例真性增大，也不要继续每张儿童片都误报。守门用例
`_test_chest_paediatric.py` 的 T5/T6 把这个偏差显式量了出来（`1.05 ≤ 估算/内缘
≤ 1.20`），避免以后被悄悄放大。CTR 上限校验取 1.0：心脏不可能比胸廓还宽，
超出即判「未能核实」而不是吐一个不可能的数字。

### 足弓关键点的手动微调（v1.9.5 新增）

足弓模型（`xray/app/core/model/foot_arch_inference.py`）返回的 P1~P5 五个
关键点常有 3~5 像素偏差，重新训练需要大量标注数据，因此留了「微调」口子：
**跑完足弓检测直接拖图上的五个手柄，拖动即时重算内侧/外侧足弓角**。

| 环节 | 实现 |
|---|---|
| 坐标约定 | 一律记在**图像像素**（x 右、y 下，与 cv2/pydicom 一致）。模型已把
  letterbox（800）与 heatmap 亚像素峰值还原回原图像素，上层不用再管缩放 |
| 模型输出 | `xray_bridge.run_foot_arch()` 在 `image` 之外额外给出 `keypoints`
  （`{idx: (x, y)}`）与 `keypoint_names`；`_blank_result()` 加了这两个键 |
| 手柄绘制 | overlay 渲染器（Layer 1，`PreserveColorBufferOn()`、`SetInteractive(0)`），
  与底图共享相机；圆环 + 实心十字 + 名称标签 + 角度读数，独立于 AI 位图 |
| 显示切换 | 进入微调态时底图切回**原始影像**（`set_ai_overlay_image(None)`）——
  AI 标注图里那些圆点是烘死在位图里的、且跟手柄位置完全重合，不切的话用户
  **看不出自己抓的是哪个**；退出时把标注图还原 |
| 拖动闭环 | 左键按下手柄（优先于测量下点）→ `mousemove` 换算回图像像素并
  即时 `move_keypoint` → 抬起结束；越界点在图像范围内被夹住 |
| 角度口径 | `Dicom2DReader.keypoint_angles()` 顶点取 P2（内侧）与 P5（外侧），
  与模型 `_compute_arch_angle()` 完全同源，微调后的读数与模型原读数对得上 |
| 复位 | `reset_keypoints()` 回到模型原始点位；被拖动的点另画一个白色「原」字
  标出模型原始位置，方便对比 |
| 多窗 | 信号 `Dicom2DReader.keypoints_changed` → `StudyViewPanel.keypoints_changed`
  → `MainWindow._on_foot_arch_keypoint_moved`；所有操作作用于 `active_reader`，
  `clear()` 会清掉所有窗的手柄 |

**换算的关键**：`_kp_spacing()` 直接读 `_ai_actor.GetInput()` 的 spacing 作为
「图像像素 → 世界坐标」的比例，与 `set_ai_overlay_image` 建标注图时用的是同一
套值，天然自洽。**不要改成依赖 `self._extent`** —— `clear()` 之后它是 `None`，
换算会静默退化成 1:1，手柄落在模型点的旁边（真实足部片实测踩到）。

**验收**：`_test_foot_arch_keypoint.py`（28 项，覆盖行序三方向 + 标注图块与
关键点的屏幕落点一致性 + 屏幕↔图像像素往返 + 抓握 + 拖动/夹取 + 与模型
同源的角度 + 复位 + 信号 → 主窗摘要 + 真实鼠标事件链 + 微调开关往返 + 四窗清理）。

### 脊柱侧弯（Cobb 角）的手动微调（v1.9.6 新增）

与足弓共用同一套「拖手柄 → 即时重算 → 复位」机制，区别只在**形态与读数**。
脊柱模型（`xray/app/core/model/spine_inference.py`）本来就是按「上下终板线
的夹角」定义 Cobb 角的，所以交给上层微调的正好是这两条线的四个端点。

| 环节 | 实现 |
|---|---|
| 模型输出 | `detect()` 在 `cobb_angle` 之外给出 `upper_line` / `lower_line` 与
  `cobb_points`（`{1,2}` 上端椎、`{3,4}` 下端椎，原图像素）；`xray_bridge.run_spine()`
  透出为 `keypoints` + `keypoint_names`（上端椎1/2、下端椎1/2） |
| 形态位 | `Dicom2DReader._kp_shape`：`"foot"`（足弓折线）/`"cobb"`（终板线）。
  `set_keypoints(..., shape=...)` 写入，`clear_keypoints()` 复位为 `"foot"` |
| overlay | 上下终板线各一条粗线 + 两条细延长线 + 交点处一个环；手柄配色
  `_COBB_LINE_COLORS`（上端椎橙、下端椎紫），与模型 `draw_results` 的画法呼应 |
| 角度口径 | `_cobb_angle_from_lines()` 直接复用模型的 `angle_between_lines()`
  （无向线朝向归一到 `[-90,90)`、再取锐角），读数为 `(Cobb, None)`；
  取不到模型时走同一套数学兜底，**手动调出来的数与模型自己的数一致** |
| 读数挂点 | 两条延长线的交点；两线近乎平行求不出交点时改挂上端椎线，不崩 |
| 回写 | 拖动经 `keypoints_changed` → `_on_xray_keypoint_moved()`；`kind == "spine"`
  时把 `Cobb角` 指标与摘要整体改写，摘要追加「（手动调整）」 |
| 复位 | `reset_keypoints()` 回模型端点。注意面板代理是 `emit=False`（防信号
  回环），主窗的「已手动微调」标记与读数由 `_on_xray_reset_kp()` 自己重取 |
| 形态互切 | 同一窗口先后跑足弓与脊柱检测时，`_xray_kp_kind` 与 `_kp_shape`
  一起换，读数口径随之切到内外侧角 / 单一 Cobb 角，互不串味 |

**两个坑**：①端点越界会被 `_kp_clamp` 夹回图内，**夹 1 像素角度就偏约 0.5°**，
验收夹具（以及贴到真实片子上）要留出行边；②`keypoint_angles()` 在脊柱形态下
第二位固定是 `None`，别拿足弓那对 `(内侧, 外侧)` 的下标去取数。

**验收**：`_test_cobb_manual_adjust.py`（45 项，覆盖行序 + 往返 + 四端点抓握 +
与模型同源角度（平行 0° / 垂直 90°）+ 拖动/夹取 + 复位 + 信号 + 真实鼠标事件链 +
微调开关往返 + 主窗脊柱口径回写 + 两种形态互切 + 走 `_on_xray_finished` 的装载
路径 + 两线平行兜底 + 四窗清理）。

#### 三处关键坑

1. **重写 `QWidget.setVisible` 会爆栈**。`setVisible` 是虚函数，Qt 内部的
   `show()`/`hide()` 就是靠调它实现的；若在 `setVisible` 里再调 `self.show()`，

   （Windows 访问违规），**不产生任何 Python traceback**，极难定位。
   现在 `show/hide/setVisible` 三个入口全部收口到 `_show_impl`/`_hide_impl`，
   这两个只调 `super().setVisible()`（C++ 实现，不会再回到 Python）。
   守门用例：`_test_loading_ui.py` 的 P10。
2. **自定义 `size()` 会顶掉 `QWidget.size()`**，布局会拿到错的尺寸。
   `TechSpinner` 里的尺寸读取接口因此命名为 `spinner_size()`。

   三维视图」这几处是同步执行，它们靠 `busy_scope.__enter__` 里的
   `processEvents` 泵出首帧，遮罩本身仍是静态好看的。

#### MR 支持的四个层次

**1. 采集层：MR 目录为什么进不来**

MRI 目录名往往是**纯 DICOM UID**（东软等设备形如
`1.2.840.31314.14143234.20251213000000.6202511807`），既没有 `_CT`/`_DX`
模态后缀，同目录也未必有 XML 清单。原`_iter_patient_dirs()` 只按后缀匹配，
导致这批检查（实测 755 文件 / 24 序列）**整体消失**。

新增兜底规则 `_looks_like_dicom_uid_dir()`：名字形如 DICOM UID
（点号分段且每段全数字）且直接含 `.dcm` 的目录一律作为候选，
真实模态随后以 DICOM 的 `Modality` 标签为准。

> **踩坑**：UID 目录名**必然含点号**，所以判据不能写成 `"." not in name`
> —— 那样会把真正的 UID 目录全部漏掉。必须用「点号分段且每段为数字」。

另有一条兜底：扫描根目录本身直接躺着 `.dcm` 时（实测有MRA 单张这么
落盘）也纳入，否则这批片子同样丢失。

**2. 层序：`vtkDICOMImageReader` 自会排序，别重复劳动**

实测结论（重要，与直觉相反）：`vtkDICOMImageReader` **自己就按
`ImagePositionPatient` 排序**堆层，与文件名顺序无关 —— 用同一批切片
分别以「字母序」和「逆序」命名临时文件，读出的逐层序列完全一致
（21/21 层吻合，且均为沿法向**降序**）。所以 MR 读出来**不会层序错乱**。

`analyze_slice_geometry()` 的实际价值是两点：

- **方向规范化**：vtk 固定给降序，而 CT 侧既有流程与「从上到下」的
  阅读习惯都是升序，不统一会导致同一部位在 CT 与 MR 上上下颠倒；
- **矢状面**：矢状面 MR 的 IPP **z 几乎恒定**，必须沿层法向投影排序。
  实测 `t2_fse_sag` 法向 ≈ X 轴、沿法向间距 6.0mm，而 z 恒为 91~97，
  只按 z 排会判定「整个序列是同一层」。

法向取 `ImageOrientationPatient` 两个行向量的叉积
（行序约定与 DICOM PS3.3 一致），无 IOP 时退回 z 轴。

**3. 窗值：MR 像素是信号强度，不是 HU**

同一头部检查里各序列的 DICOM 窗值量级差异极大：
FLAIR `WW757/WL380`、T2 `WW1998/WL1000`、ADC **`WW3578/WL1615`**。

CT 的合理性校验是 `1≤WW≤6000` 且 `-1500≤WL≤1500`，会**拒绝 ADC 的
真实窗值** → 兜底成 400/40 → 整幅发黑。故 MR 走独立策略
（`mr_window_level()`）：DICOM 自带窗值 → 序列类型预设
（`MR_WINDOW_PRESETS`）→ 像素 p1~p99 分位数。

同时**禁用 CT 专属控件**：肺窗/骨窗等HU 预设、骨阈值（50~500 刻度）、
CT 值测量 —— 套到信号强度上不是全黑就是全白，纯属误导。

`mr_series_kind()` 把序列分成 mra / dwi / adc / t1 / t2 / flair / pd。
> **踩坑**：序列名 `epi_dwi_tra_ADC` 同时含 `dwi` 和 `adc`，**必须先判
> adc** —— 两者窗值差一个数量级（ADC 的 WW 达 3578），分类错了窗值就跟着错。

**4. MRA 血管三维：阈值不能用分位数**

初版按 p92 取阈值，离屏渲染出来是**整个头颅的软组织壳**（表面碎片
11434 片），根本不是血管。原因是这批 TOF 序列的脑组织背景本身就很亮
（全幅 p90 已达 206），血管不是「最亮的那一撮」。薄层原图目视确认：
血管在 Willis 环附近只是几个小白点，脑实质亮度甚至高于血管；
真正明亮的血管树在设备的 `tof3d_tra_MRA_MIP` 序列里。

从薄层重建血管只能靠**绝对高阈值**把血管「烧」出来。标定依据是
**p99.9 的倍数**而非 max（max 是单点极值：实测 1323，而 p99.9 才 418、
p99.99 才 790，按 max 定标会被单点噪声拉偏）：

| 阈值 | 最大连通域占比 | 表面片数 | 效果 |
|------|--------------|---------|------|
| 298（p92）| 18% | 11434 | 脑组织壳，不可用 |
| 350 | 46% | — | 尚可 |
| **400** | **63%** | **35** | **形态最佳** |
| 500 | 36% | 30 | 开始丢末梢 |

最终 `mra_vessel_threshold()` 取 `p99.9 × 1.05`，并带「保留量过少则
逐档下调」的兜底。离屏渲染实测可得到完整脑血管树
（Willis 环 + 大脑前/中/后动脉 + 颈内动脉颅外段）。

#### 不可堆层序列的识别

MR 检查里混着两类**不是断层**的东西，加载后三维必然崩坏：

- **重建批次**（`3D_Batch1/2`，1520×1520，25 张）：所有切片 IPP
  **完全相同**，沿法向投影间距为 0 —— 是同一张体数据被切成多批渲染的
  中间产物；
- **定位像**（`gre_scout`，3 张正交定位图）：层间距 130mm。

判据 `is_stackable_series()`：张数 ≥2、投影间距中位数 ≥0.05mm、
且 ≤20mm。**注意判定位像要看序列名而不是层厚** —— MR 的 scout 在
`SliceThickness` 里写的是 8mm（看着像正常断层），但实际层间距 130mm。

`mr_series_readable()` 在采集阶段就滤掉这些序列（24 → 16 个），
单张 MR 序列（MRA 的 MIP 投影图）保留供阅片，但禁用三维入口。

#### 「数据维度异常」：单张 MR 不能按 CT 的体数据约定拦截

`DicomLoadWorker` 沿用 CT 的约定：Z 维必须 ≥2 层，否则抛
「DICOM数据维度异常」。这对 CT 合理（单层 CT 序列是数据异常），
**但 MR 存在合法的单张序列** —— 实测有 MRA 的 MIP 投影图直接躺在
扫描根目录下（张数为 1），是正常影像而非坏数据。
初版忘了给 MR 放行，用户双击该序列直接报错打不开。

修复按张数精确判断，而非对 MR 无条件放行（保住「MR 真的损坏时
仍要拦住」的能力）：

| 模态 | `allow_single_slice` | 理由 |
|------|--------------------|------|
| CT | `False` | 单层是数据异常，原本就该拦 |
| X 线 | `True` | 一幅片子就是一个序列，Z 维必然为 1 |
| MR | `len(file_uids) <= 1` | 单张序列是合法影像；>1 张却只读出 1 层说明数据真有问题 |

单张 MR 与单张 X 线的三维入口由 `set_3d_available(False)` 单独禁用，
两件事互不影响。

> **测试盲区教训**：本项最初没被测出来，是因为 `T12` 只断言了
> 采集结果（单张序列"出现在列表里"），却没断言**加载路径能通过**。
> 数据通路通过 ≠ 加载路径通过 —— 凡是「列表里能看到」的序列，
> 都必须有一条「能真的读出来」的断言（T14）。

一次 MR 检查里同名序列很常见（实测某头部 MR 有两个都叫

### v1.8.0 (2026-10-04)
- **修复：勾选「去除细小碎屑」后三维图像质量明显下降、看起来都是纹路**。

  **根因**在 `filter_bone_components()` 写掩膜体数据的那两行：

  ```python
  bg = min(int(arr.min()), int(iso) - 1)      # 例如 -1024
  if removed_debris:
      out[~keep[labels]] = bg                 # ← 问题在这里
  ```

  `keep[0]` 恒为 `False`（背景 cid=0 的连通域尺寸为 0，低于剔除阈值），
  所以 `~keep[labels]` 覆盖的是**整个背景**，而不只是被剔除的碎屑 ——
  背景体素被一并砸成了 `arr.min()`。

  背景恰恰承载着**阈值附近的 HU 梯度**，而等值面位置正是由
  「阈值以下体素 ↔ 阈值以上体素」的线性插值决定的。以 iso=200 为例：

  | 体素 | 原始 HU | 与 400 HU 骨体的插值点 t |
  |---|---|---|
  | 背景体素 | 190 | `(200-190)/(400-190)` = **0.05**（贴近骨面） |
  | 背景体素 | 0 | `(200-0)/(400-0)` = 0.50 |
  | 被砸平后 | -1024 | `(200+1024)/(400+1024)` = **0.96**（缩到骨体内部） |

  也就是说，等值面**整体向内收缩了近一个体素**；而每个体素收缩多少，
  取决于它原本离阈值多远 —— 这层原本平滑的梯度被**逐体素放大成抖动**，
  渲染出来就是满屏横向条纹（用户反馈的「看起来都是纹路」）。
  同时一个连通的面被打散成大量碎片。

  **修法**：显式排除背景，只写被剔除的连通域体素，填充值取 `iso-1`
  （足以让剔除区不产生新等值面，又不破坏周围 HU 梯度）：

  ```python
  debris_mask = keep.copy()
  debris_mask[0] = False          # 背景 cid=0 恒不剔除
  debris_mask[1:] = ~keep[1:]
  out[debris_mask[labels]] = np.int16(iso - 1)
  ```

  `bed_cids`（床体整块删除）与 `cut_lo`/`cut_hi`（半空间切除）三处同样处理。

  **实测对照**（同一条真实序列、同样只删 867 个体素，唯一差别是背景是否被改）：

  | 填充策略 | 4286 表面片数 | 4243 表面片数 |
  |---|---|---|
  | 修复前（砸平背景） | 632 | 95 |
  | 修复后（只填碎屑） | **332** | **62** |
  | 完全不过滤（对照） | 332 | 69 |

  修复后表面片数不涨反降（69→62），即碎屑被干净剔除、表面反而更整洁；
  离屏渲染确认条纹消失、骨面光滑连贯。

  **通用铁律**：任何「把某些体素改成背景值」的滤波，都必须显式排除
  `labels==0` 的背景体素 —— 背景不是「要被清理的空白」，而是插值的依据。

- **修复：勾选框提示与实际参数不符**。「去除细小碎屑」的说明原写
  「骨表面 2 个体素内的噪声壳层受邻接保护」，实际邻接保护距离是 6 个体素，
  已更正（避免误导调参）。

- **验收判据升级**：三维质量问题现在除体素统计外，增加
  **表面独立片数**（`vtkPolyDataConnectivityFilter` 的 regions 数）——
  它对「表面被打碎」远比对体素数量敏感（同样删 867 个体素，
  632 vs 332 一眼可辨）。单测 `_test_filter_v3.py` 新增 T16/T17

### 1. 多窗同步（翻层 + 窗值联动）

## v1.9.0 第二次修复（用户实测反馈）

### 1. 打开 DICOM 无反应、也无提示（真 bug）
**根因**：`_load_single_dicom_file()` 里写了 `U.is_mr_modality(...)`，
但 `main.py` 是**按函数直接导入**的（`from ct3d_utils import is_mr_modality`），
模块名 `U` 根本不存在 → `NameError`。而它被 `except Exception` 吞掉
只 `print` 到控制台，**界面上什么提示都没有**。

> **铁律：`except` 里的 `print` 对用户等于静默失败。**
> 用户看不到的控制台输出不构成任何反馈 —— 所有用户可触发的失败路径
> 都必须弹 `QMessageBox`。已给 `_load_single_dicom_file` /
> `_open_path` 补上提示（含建议：单张片子可用「打开 DICOM 文件」）。

### 2. 「加载患者目录」报「DICOM数据维度异常」（真 bug）
**根因**：判据只按「直属 dcm 数量 ≥2」判单序列，但设备有些目录把
**多个序列混放**在一起。实测 `01/` 目录 13 张实含 **4 个序列**
（Cervical-spine 2 + Thoracic-spine 2 + Lumbar-spine 3 + Thoracic-spine 6），
`vtkDICOMImageReader` 只会挑其中一个序列读（实测 Z 维仅 2，其余被丢弃）
→ 抛「DICOM数据维度异常」。

**修法**：`is_single_series_dir()` 改为按**本目录直属的实际序列数**判定
（`_series_index_uids()` 是非递归的，正好可用）：

| 条件 | 判定 | 行为 |
|------|------|------|
| 直属 dcm ≤ 1 | 非单序列 | 刷新列表（单张请用「打开 DICOM」） |
| 序列数 == 1 | 单序列 | 直接打开 |
| 序列数 > 1 | 非单序列 | 刷新列表 |
| 索引失败 | 回退：≥2 张且同层无子目录 | 直接打开 |

> **判据不能拿「有无子目录」当**：曾加「有子目录就排除」的规则，结果把
> 755 张 24 序列的 MR 目录也排除了（它内部恰好有 1 个子目录），真序列
> 反而打不开。**子目录与序列数无关。**
> 实测这台设备**所有**大目录都是多序列混放（755/24、1599/6、1044/5、
> 289/4、198/5、1060/5、407/5），按「dcm 数量」判序列目录必然出错。

### 3. 二维窗左右方位字重复叠加
**根因**：`quad_viewer()` 里 `self._layout.addWidget(self._quad_viewer, 1)`
与二维网格容器 `_view_grid_host`（也在 index=1）**挤进同一格**，
两者都可见时，`QuadViewer` 里 3 个 `SliceView` 的「右/左」与
`Dicom2DReader` 的「右/左」同时显示。

**修法**：三维视图装进**独立 host 容器** `_quad_host`，
`_apply_visibility()` 严格互斥（2D 藏 host / 3D 藏网格）。

### 4. 左下角层数遮挡「序列」按钮
**根因**：`fullscreen_btn` / `_strip_btn`（「序列」）/ 测量工具栏
三者都排在**左下角**，而 `_bl_label`（层数）也在左下角 —— 实测全部重叠。

**修法**：`_position_widgets()` 把三个控件中**最高者的顶部**作为
遮挡线 `occluded_from_y`，传给 `_position_overlays()`；
角标与方位字一律排到该线**之上**，窗口太矮时贴上边也**绝不压按钮**。

### 为什么要同步

**日常一律用 `--sync`**：按内容哈希（MD5）逐个比对，只覆盖真正变化的文件，

1. **按 MD5 比对** `SYNC_FILES` 列表里的文件，只拷贝变化的
   （大小相同不代表内容相同，必须比哈希）；
2. **同步自检脚本的版本断言**：把 `_release_selfcheck.py` 里硬编码的
   `APP_VERSION == "v1.x.x"` 改成当前版本，否则自检会误报「发行版损坏」；
3. **清理发行目录里的陈旧 `.pyc`** —— 代码更新后旧字节码缓存会遮蔽新行为。

另外会对只读目标文件自动 `chmod 0o666`（从压缩包解出来的文件常带只读位）。

## 二维多窗显示（v1.9.0 新增，1 / 2 / 4 窗）

### 目标
临床常要并排对比同一检查的多个序列（头部 MR 的 T1/T2/FLAIR/DWI、
CT 的不同窗位、术前术后对比）。原二维区只有一个 `Dicom2DReader`，
一次只能看一个序列。

### 实现方式：多个独立 reader + QGridLayout
`StudyViewPanel` 把原来「直接放一个 reader」改成「网格容器`_view_grid_host` +
`QGridLayout`」：

- **索引 0 是主窗口**，沿用既有引用名 `_reader_2d` —— MainWindow 与多处
  代码依赖它，保持不变即可**零回归**；
- 索引 1..N-1 是副窗口，各自是完整的 `Dicom2DReader` 实例
  （自带 VTK 控件、测量层、窗值、缩放平移），互不干扰；
- 窗口数 `_view_count`（1/2/4）与实例数 `len(_readers_2d)` **是两个概念**：
  切回 1 窗时实例与数据都保留，只是隐藏，便于来回对比。

### 活动窗口（`_active_view`）
多窗下所有操作都要有个"作用于哪个窗"的语义：

| 操作 | 归属 |
|------|------|
| 双击/拖放序列卡载入 | 活动窗口（`set_data(view_index=...)`） |
| 窗宽窗位调节 | 活动窗口（各窗窗值本就不同，强行同步会抹掉用户调好的对比度） |
| 滚轮/方向键/滑条翻层 | 活动窗口 |
| CT 值/长度/角度测量 | 活动窗口 |
| AI 标注叠加 | 活动窗口（只针对刚检测的那张片子） |
| CT 测量工具**可用性** | 所有窗统一（工具开关是全局的） |
| 视图复位 | 所有**可见**窗口（每窗记录自己的相机状态） |

活动窗口通过 `eventFilter` 捕获 `MouseButtonPress`/`FocusIn`/`Wheel`
自动跟踪，并给活动窗加**蓝色边框**明示。

副窗口的 `slice_changed` **不再冒泡**给 MainWindow（只就地更新本窗层号），
否则状态栏会被副窗的翻层事件带着走。

### 三个必须注意的实现陷阱

1. **不能新增同名的 `eventFilter`**。
   `StudyViewPanel` 原本已有 `eventFilter` 负责**把 VTK 原生窗口的拖放事件
   转发给面板**（VTK 子窗口不参与 Qt 事件冒泡）。初版又写了一个同名方法
   用来跟踪活动窗口，Python 同名方法只保留最后一个 → **拖放功能静默失效**。
   正确做法：合并进原有的一个。已加断言（T18）防止复发。

2. **`QGridLayout.itemAt()` 返回 `QWidgetItem`，没有 `setSizePolicy`
   / `sizePolicy`** —— 尺寸策略要设在 `item.widget()` 上，
   否则均分空间失效、窗口挤在一起。

3. **`_layout_readers()` 不能用 `isHidden()` 反推窗口数**。
   `set_view_count` 建新窗时已经 `hide()` 了它们，据此算会永远得到 1
   （曾表现为「切到 4 窗但只显示 1 个」）。窗口数必须由 `_view_count` 给出。
   同理 `view_count()` 返回的是 `_view_count`（显示中的窗数）而非实例数。

### 拖放必须按「落点」定位目标窗（v1.9.0 用户实测修复）

初版 `dropEvent` 只把序列 token 抛给 MainWindow，**丢掉了落点信息**，
于是无论拖到哪个窗都载入活动窗口 —— 表现为「往右窗拖新序列，
原来那窗的序列被覆盖了」。

修法：`view_index_at(pos)` 按鼠标落点反查所属窗口，并把索引
一起传下去（`series_dropped` 改为两参数信号）。反查有两处陷阱，
都实测踩过：

1. 宿主 `_view_grid_host` 是**普通 QWidget**，`indexAt()` 是
   `QStackedWidget` 专有的方法 —— 直接 `AttributeError`；
2. 改用 `childAt()` 后**仍恒返回 0**：`Dicom2DReader` 是 QFrame
   容器，落点命中的是它**内部**的子控件（VTK 原生渲染控件、翻层滑条、
   覆盖层标签等，实测单个 reader 有 24 个子控件），不是 reader 本身。
   必须沿 `parentWidget()` 链上溯（`_reader_index_of()`）。

> 教训：Qt 的坐标命中判断不能想当然，**必须用真实几何验证落点反查**。
> 第一版「看起来对」的实现在真实布局下恒返回 0，是靠手动
> `setGeometry` + 按点探测才抓出来的。

### `quad_viewer` 是方法，不是 property（v1.9.0 用户实测崩溃）

加多窗时给 `quad_viewer` 误加了 `@property`，而 MainWindow 侧有
**4 处**按 `quad_viewer()` 调用（连MPR 信号、渲染刷新、
`_apply_visibility`、`_ensure_volume`）→ 用户一操作就弹
`TypeError: 'QuadViewer' object is not callable`，全局 excepthook
只能弹框、程序不退出（符合「槽函数里未捕获异常 = 静默闪退/报错框」
的既有模式）。

已去掉 `@property`，并在 T18 加 AST 断言防复发。

> **通用铁律：给已有方法加装饰器前，先全局搜一遍调用点。**
> 方法↔属性只差一个括号，编译器与 `py_compile` 都查不出来。

### 各窗数据必须隔离（v1.9.0 用户实测修复）

症状：2 窗模式下，序列 1 拖到 a 窗、序列 2 拖到 b 窗，
**a 窗的序列 1 消失了**。

根因：`_load_series()` 开头无条件调 `self._study_panel.clear_all()`，
而多窗改造时该方法被改成「清空**所有**窗口」→ 往b 窗载序列时
连带清掉了 a 窗。

修法两处：
1. `clear_all(view_index=None)`：给索引只清那一个窗；`None` 保持
   「全清」语义（关闭整个检查时用）。主窗被清时若其它窗仍有数据，
   工具栏按钮保持可用。
2. `_load_series` 先取 `_target = self._study_panel.active_index`，
   `_target == 0` 才走全局清理（作废三维管线/ 分割掩膜 / 模态标记），
   否则只清该窗。

**顺带修一个更隐蔽的隐患**：`_last_temp_folder` 原是**单个槽位**，
多窗下各窗的 `DicomLoadWorker` 会各自建暂存目录（MR 强制暂存、
目录不纯净时也会），载第二窗时会覆盖并**删掉**第一窗的暂存目录 ——
那一窗的 reader 还指着它，图像会随之失效。
改为按窗口记录 `_view_temp_folders: {窗口索引: 目录}`，
新增 `_all_temp_folders()` 统一收集，`closeEvent` / `_on_close_current`
关闭时一次性清理；换窗时只清该窗自己的旧目录。

> 附带发现：`Dicom2DReader.clear()` 内部会 `render_win.Render()`

## PACS 导出目录读取（v1.9.7）

### 现象

科室从 PACS 导出影像后，工具栏「加载患者目录」选目录读不出影像。本机两个
样本目录各对应一条**互不相干**的根因：

| 目录 | 形态 | 旧行为 |
| --- | --- | --- |
| `D:\ClearTmp\DicomTmp\02` | 8 张扁平 `.dcm` 的 DX（`2012x2012`） | 读出一块 64x64 黑图、翻层是同一小块 |
| `D:\ClearTmp\DicomTmp\04` | 顶层 0 文件，图片躺在 `Untitled-0/-1/-2` 里 | 「未找到CT薄层序列」 |

### 根因一：02 —— `vtkDICOMImageReader` 被 (0088,0200) 坑成 64x64

文件本身**完全合法**：pydicom 能读、`Transfer Syntax` 齐全
（`1.2.840.10008.1.2.1` Explicit VR LE）。但 VTK 的 DICOMParser 遇到
**(0088,0200) PresentationStateReferenceSequence** 会解析到一半放弃，
`Rows/Columns` 始终没赋值 → 退回默认 64x64。

定位方法是「逐元素二分」：固定「必填图像头 + 完整像素」不变，逐个往
`Dataset` 里加非图像元素，一加 (0088,0200) 就立刻从 2012x2012 掉到 64x64。

上层拦不住的原因也很清楚：Z 维**还在**（8 层），所以既有那条
`extent[5]-extent[4] <= 0 → DICOM数据维度异常` 完全不触发。

**两处兜底（缺一不可）：**

1. **`_load_series` 先做 modality 探测**（`_analyze_series_from_dicom_fast`）。
   原先「加载患者目录」调 `_load_series(folder)` 不传 `series_data`，
   modality 恒空 → DX 被当 CT 交给 VTK。现在探测到 `DX/DR` 直接走
   `XraySeriesReader`（pydicom 装配）。探测失败也不拦，按原路径加载。
2. **加载线程里做 VTK / pydicom 尺寸交叉校验**（`DicomLoadWorker`）：
   `_header_dims(folder)` 只 peek 前 6 张的**文件头**（`stop_before_pixels=
   True`，千张序列也快）取 `(rows, cols)`，跟 VTK 读出的 extent 对一遍，
   不一致就换 `XraySeriesReader` 重读一遍。

> **踩过的坑（一）**：`_header_dims` 返回的是 `(rows, cols)`，而 VTK extent
> 的 X 是**列**、Y 是**行**。非方阵（如 96x128）在这里写反，会把「读对了」
> 误判成「读错了」，白白触发一次无谓的 pydicom 重读。v1.9.7 已改对，
> 并用合成用例 A1~A3 卡住（合成目录故意造了个 96x128 的非方阵）。

> **踩过的坑（二）**：合成夹具不可信。`vtkDICOMImageReader` 对**自造**的
> DX 文件连几何都判不准（实测 4 张 96x128 只出 1 层；真实文件的副本改成
> 96x128 后反而退成 64x64x4 —— 64x64 是默认值）。所以合成用例只校验 x/y
> 与「没走兜底」，层数可靠性由真实样本 E3 保证。

### 根因二：04 —— 散图目录从来没进过任何扫描口径

8 张独立 JPG，尺寸各异（2792x2524 / 2984x2272 / …），既不是单序列目录、
也不是患者根目录：`is_single_series_dir` 只认直属 `.dcm`，
`collect_ct_patients` 只看目录名后缀或 UID 目录名。

**新增：**
- `ImageSeriesReader`（目录图片当序列）。尺寸不齐时补到公共网格，取法是
  **严格多数派**（`top*2 > len`），平局取面积最大；补边居中，且 `arr`
  比网格还大时**先居中裁中心**再写入（否则 `(2792-2984)//2 = -96` 的
  负下标会广播出只有 96 行的残图）。
- 模块级 `dir_image_files` / `image_subdirs` / `is_image_only_dir`。
- `_open_dir`：把「加载患者目录」与「打开影像文件→目录」两份重复决策
  收口成一份，四条分支（纯 DICOM 单序列 → 直接开；纯图片目录 → 整目录当
  图片序列；图片在子目录 → 问一句并加载**张数最多**的那个；否则 → 重建
  序列树）。

> **踩过的坑（三）**：`image_subdirs` 最初按名字排序返回、`_open_dir` 取
> `subs[0]`，结果 04 选到只有 2 张的 `Untitled-0`，而实际最多的是 `Untitled-2`
> （4 张）——文案说的是「张数最多的那个」，行为却是「名字最靠前的那个」。
> 现改为 `max(subs, key=lambda s: (s[1], s[0]))`。

## v1.13.0：本轮四项改动（Win7 兼容 + 交互改进）

### 一、Win7 上「点漏检反馈按钮弹错」的根因与修复

#### 现象

Win7 机器上点击「漏检反馈」或「反馈列表」按钮弹出错误框；同版本在 Win10/11
上正常。开发机（走 `run_env.bat` 启动）复现不出来。

#### 根因

桌面快捷方式由 `install.bat` 调 `CreateShortcut.vbs` 生成，**直接执行**
`pyenv\pythonw.exe main.py`，**绕过了 `run_env.bat`** —— 于是进程继承的是
Windows 系统 PATH，而不是 `run_env.bat` 里设置的：

```
PATH=%~dp0\pyenv;%~dp0\pyenv\Library\bin;...
```

而嵌入式环境里的第三方扩展模块**依赖 `pyenv\Library\bin` 下的配套 DLL**：

| 模块 | 依赖 | 缺失时的报错 |
|---|---|---|
| `sqlite3` | `pyenv\Library\bin\sqlite3.dll` | `DLL load failed while importing _sqlite3` |
| `pydicom` | `pyenv\Library\bin\libcrypto*.dll` | `module 'lib' has no attribute ...` |

`FeedbackStore` / `DetectionRecordStore` 都用 `sqlite3` 存库，所以**只有反馈
功能受影响**（其它功能不碰 SQLite），这正是「点反馈按钮才出错」的原因。

#### 修复

新增 `runtime_env.py`，在**进程最早期**（任何扩展模块 import 之前）修正
DLL 搜索路径：

1. `os.environ["PATH"]` 前置 `pyenv\Library\bin` 等目录 —— 兼容所有平台
2. `os.add_dll_directory()` 注册显式搜索目录 —— Python 3.8+ / Windows
   （本项目正是 3.8.3；Win7 需 KB2533623，未打补丁时该调用抛 `OSError`，
   静默忽略、仅靠 PATH 兜底，Win7 上同样有效）
3. 顺带补 `QT_PLUGIN_PATH`

**要点**：`os.add_dll_directory()` 返回的句柄**必须持有引用**，否则被 GC 后
目录立即失效 —— 模块级列表 `_DLL_HANDLES` 就是干这个的。

在 `main.py` 与 `xray_bridge.py` 顶部各调用一次 `runtime_env.bootstrap()`
（幂等）。`xray_bridge.py` 里的调用保证即使单独使用该模块也能自愈。

另外补了两层防护：

- `xray_bridge._import_sqlite()`：导入失败时自动补一次 DLL 路径再重试
  （自愈），仍失败则抛带**中文说明**的 `RuntimeError`，而不是抛
  `ImportError: DLL load failed` 这种天书
- `xray_bridge.probe_sqlite()`：UI 在打开反馈窗口前先自检，失败时弹
  「反馈数据库不可用：……」并提示改用 `启动程序.bat`

#### 验收

- 干净 PATH（`PATH=/c/Windows/System32:/c/Windows`）下 `import sqlite3`
  成功、`probe_sqlite()` 返回 `(True, "")`、反馈库可读可写
- 干净 PATH 下 `main.py` 可完整导入
- `_release_selfcheck.py` **PASS 49 / FAIL 0**

### 四、工具按钮图标化 + 汉字悬停提示

#### 为什么要画图标而不是放资源文件

### 二、OCR 引擎：为什么自实现而不装 rapidocr

宿主 `pyenv` 已有 `onnxruntime 1.12.1 + opencv 4.12 + numpy + PyYAML + pillow`，
但官方 `rapidocr-onnxruntime` 依赖 `pyclipper` + `shapely`（DBNet 后处理的
多边形裁剪），引入它们要动发行包的 Python 环境。

`ocr/ppocr_engine.py` 用 cv2 等价替代：
`threshold → dilate → findContours → boundingRect`。
报告是规整横排文字，不需要精确的多边形轮廓，实测识别结果与官方一致。

**三个必须对齐的口径**（漏一个就表现为「高置信度乱码」）：

| 口径 | 做法 | 漏掉的后果 |
|------|------|-----------|
| CTC 字符表 | 首插 `blank`、尾插空格 | argmax 索引整体偏移 1 位 |
| rec 输入宽度 | 按 batch 内最大宽高比**动态**算 | 长行（宽高比 21:1）被压扁 |
| det 框映射 | `box / bitmap_w * W` 回原图尺度 | 32 对齐使 blob ≠ 原图，框整体偏移 |

模型无需 IR 降级：三个模型本身是 ir_version 8/7、opset 12/11，
ORT 1.12.1（IR 上限 8）直接加载。

### 三、字段提取：针对真实 PACS 界面的适配

真实界面是「标签：值」网格 + 两个大文本框（影像所见 / 诊断结果）+ 右侧面板
+ 底部按钮行。`pacs/fields.py` 处理四个现实问题：

1. **一行多对**（姓名/性别/年龄同行）—— OCR 给出多个 box，先按 y 聚类成
   逻辑行（容差取行高的 0.4，用 0.6 会把相邻两行并成一行），再按标签位置
   把逻辑行切成多对逐一提值。`^` 锚点的正则做 `finditer` 找不到行内标签，
   需另建一份去掉 `^` 的标签表。
2. **标签与值被拆成两行**（OCR 裁掉半个字符时常见）—— 标签行未取到值时，
   向下找第一个「不像标签」的行补值。
3. **右侧面板与底部按钮文字与正文 y 重叠** —— 用标题行 x 定义正文栏右边界
   （标题 x + 45% 图宽），底部 UI 行按双空格拆段逐段过滤停用词。
4. **同名标签多次出现**（基本信息区 vs 右侧面板下拉）—— 第一个非空值生效。

### 四、分级与颜色（pipeline → mini_window）

| 结论 | 颜色 | 触发条件 |
|------|------|---------|
| 危急 | `#dc3545` 红 | 命中危急值标准（10 类） |
| 修改 | `#e8850c` 橙 | 高危错别字，且所在 OCR 行置信度 ≥ 0.85 |
| 复核 | `#d8b90a` 黄 | 中低危错别字 / 逻辑 / 语法 / 字段缺失 |
| 通过 | `#28a745` 绿 | 无问题 |

**OCR 置信度门控**：错别字命中时回查该词所在 OCR 行的置信度，低于 0.85
降为「识别存疑」提示。危急值**不做**此降级——危急值关键词笔画清晰、
上下文冗长，实测几乎不受形近字混淆影响。

形近字混淆是本方案固有的误报源（实测复现：原文正确的「膈肌」被 OCR 认成
「隔肌」，而规则库恰把「隔肌→膈肌」当高危错别字）。缓解手段：
置信度门控 + 详情窗标记误报 + 忽略词表。

| 表 | 用途 |

## v1.16.0：常驻悬浮小窗 + 识别区域持久化

### 为什么要改

v1.14.0 的流程是「点按钮 → 全屏框选 → 识别」，每次都框一遍。实际使用时
医生是**在同一台机器上反复看不同报告**，报告区位置几乎不变，反复框选纯属
浪费。v1.16.0 把交互改成**常驻**：

```
程序启动 ──► 小窗自动出现（就绪态，不识别）
                 │
     首次 ──► 点「设置区域」框选一次 ──► 存 QSettings ──► 立即识别
                 │
     以后 ──► 点「刷新」或双击小窗 ──► 按保存区域截图 ──► OCR ──► 质控 ──► 显示
```

### 关键设计决策

| 决策 | 理由 |
|------|------|
| **启动只显示就绪态，不自动识别** | 程序刚起来时主窗口是最大化的，很可能正好盖住 PACS 报告区；自动截图会截到**本程序自己的界面**，OCR 出的「患者信息」是错的。让用户多点一次刷新，比给出一个错误患者信息安全得多 |
| 区域存 **QSettings**（`HKCU\Software\ZhiGu\CT3D`），不进业务库 | 区域是纯本机 UI 偏好；业务库 `report_qc.db` 在软件目录，只读环境会回退 `%APPDATA%`，位置会飘。QSettings 免安装免提权也能写，与 mini_window 的窗口位置共用命名空间 |
| 加载区域时校验**尺寸下限 20px** 和**是否落在某个屏幕内** | 换显示器/改分辨率后旧坐标可能完全在屏幕外，截出来是黑的；此时当作「未设置」，引导重设 |
| 双击刷新只认窗口空白区 | 列表条目要响应单击展开，按钮要响应点击；它们自己 accept 事件后不会冒泡到窗口，所以不会误触发 |
| 「刷新」做成蓝色主按钮 | 它是高频操作；「设置区域」是一次性配置，弱化成普通按钮 |

### 新增/改动文件

## v1.17.0：误判学习真正生效 + 自定义错别字 + 缩写误报修复

用户实机反馈三条，全部复现后修复。

### 问题 1：标记为误报后「不学习」

**现象**：详情窗点「标记为误报」，下次检测照样报同一条。

**根因（两层）**：

1. `pacs/pipeline.py` 里**一个字节都没读** `learning_records` —— 打标只写不读，
   属于「有表没有链路」。
2. `checker_base._load_false_positives_from_db()` 依赖 `qc/database_manager.py`，
   这个模块**根本不存在**（来自原 report 项目），`DATABASE_AVAILABLE=False`，
   于是 `learned_patterns['false_positives']` 恒为空，
   `checker_typo` 里那两处 `is_false_positive()` 判断恒返回 False —— 死代码。
3. 更细的一层：`learning_records.word` 存的是**整条 message**
   （「「纵膈」应为「纵隔」」），跨报告根本不会重复，拿它比对等于没学。

**修法**：

| 位置 | 改动 |
|------|------|
| `qc/database.py::extract_issue_word` | 新增。按 message 格式抠关键词：「「纵膈」应为「纵隔」」→ 纵膈；`…: 'asdf'` → asdf |
| `qc/database.py::set_verdict` | 存**关键词**而非整条 message；`false_positive` 时自动 `add_learned_word` |
| `qc/database.py` | 新增 `get/add/remove_learned_word`（存 `qc_settings.learned_words`，与 `ignore_words` 分开，便于区分「主动忽略」和「误判学到」） |
| `pacs/pipeline.py::run_pipeline` | 新增 `learned_words` 参数，与 `ignore_words` 合并后走同一个 `_apply_ignore` |
| `reportqc_bridge._pipeline_job` | 每次运行都从库读四类规则并传入 |

**为什么把学习逻辑放在数据层**：详情窗、历史窗、小窗三处都能打标，
放在 `set_verdict` 里只有一处实现，不会出现「从这个入口标记会学、
从那个入口不学」。

### 问题 2：找不到自定义错别字入口

`custom_typos` 表和 `add/list/remove_custom_typo` 早就写好了，但**没有任何 UI**
能进，且检测链路也不读 DB 里的这份 —— 只有 `config/custom_typos.json` 生效。

修法：

* `settings_dialog.py` 重写为两个页签（常规 / 自定义规则），
  「自定义错别字」做成表格 + 添加行（错词 / 正确写法 / 级别）；
* `SmartTextChecker.apply_user_rules(custom_typos, extra_terms)` 作为唯一注入口；
* `run_pipeline` 每次调用前注入 —— checker 是缓存复用的，
  **不注入就是「加词不生效」**。

### 问题 3：医学英文缩写被误报

**现象（实测复现）**：`ECT / TACE / VATS / DTPA / RADS` 全被报成
「随机误输入字母」`severity=medium`（黄灯），一份正常 CT 报告能出 3 条。

**根因**：`checker_typo.py` 里有两套互不一致的判据

| 位置 | 判据 |
|------|------|
| `_check_meaningless_input`（warnings） | 启发式：缩写表 + 随机特征 |
| 4.1 段（typos） | **硬编码 `common_terms` 白名单反查，不在表里就报** |

第二套是「白名单反查」——影像报告里缩写密度极高，白名单永远补不完，
必然误报。而且两处各有一份独立的缩写表，改一处另一处不变。

**修法（策略变更，不是补白名单）**：

* 改为**举证式判定**：默认认为拉丁字母串是医学术语，
  只有出现明确乱码证据才报 —— 键盘连按、连续 3 个相同字符、
  连续 4 个以上辅音、全元音长串；
* 新增 `_is_known_medical_term()`：内置缩写表 → 用户白名单 →
  罗马数字/脊柱分段 → **全大写 2~6 字母**（缩写典型形态）自动放行，
  但键盘连按（ASDF）和连续重复（AAA）除外；
* 两处判据统一调这两个方法，删掉重复的硬编码表（`common_terms` 两份）；
* 随机字母问题从 `medium` 降为 `low`（它本来就不是错别字，是提示）；
* 4.2/4.3 段（「中文+字母」）增加两条短路：字母是已知术语 → 不报；
  字母是已报乱码 → 不重复报。

### 顺带修掉的噪音

同一个乱码原来被报 3 次：4.1 报 `asdf`，4.2 报 `双肺纹理asdf`，
4.3 报 `双肺纹理asdf清晰`。修法是在 4.2/4.3 入口短路——
凡已被 4.1 判为乱码的字母串，不再以「中文+字母」形式重复报。

## v1.18.2：报告质控小窗精简（状态条并入标题栏）

### 为什么要改

v1.16.0 的小窗是「标题栏 + 患者卡 + 44px 状态条 + 问题列表 + 按钮条」五段结构。
上线后发现两个问题：

1. **状态条太占地方**。44px 里只有「危急 / 修改 / 复核 / 通过」一个字块 + 一句
   提示，而它下面紧跟着就是问题列表 —— 医生真正要看的是问题本身。就绪态
   （启动后还没识别）时，44px 全是「就绪」「已设置识别区域」这种信息量极低
   的内容，窗口 260px 高里近 1/6 是空的，压在 PACS 角落反而挡报告。
2. **区域尺寸是纯噪音**。原来就绪态在状态条副行显示 `760 × 900 @ (40,60)`，
   这是给开发调试看的。医生设过区域就不会再关心它；显示出来只是让用户多读
   一行看不懂的数字。

### 改法

| 位置 | 改前 | 改后 |
|------|------|------|
| 状态展示 | 44px 独立状态条：56×32 色块 + 13px 粗体结论文 + 10px 副行 | 标题栏内 17px 胶囊 + 10px 单行小字，**整条删除** |
| 胶囊宽度 | 固定 56px（两字/三字都被撑着） | 按文字实测宽度 + padding，`setFixedWidth` |
| 胶囊前景色 | 恒白字 | 按背景亮度自动选黑/白（`_contrast_fg`） |
| 区域尺寸 | 就绪态副行显示 `W × H @ (x,y)` | 不显示；`show_ready()` 的 `region_desc` 参数保留但忽略 |
| 空行 | 患者卡的第二三行、空列表提示恒占位 | 空内容直接 `setVisible(False)`，不占高度 |
| 就绪态窗口高 | 260px（下限） | 188px（下限 188，实测正好贴住 content） |

### 关键实现

```python
def _set_badge(self, text, bg="#3d3f41", fg=None):

```

`resizeEvent` 里重算，避免窗口尺寸变化后省略号位置不对。

## v1.19.1：小窗年龄去重「岁」+ 影像号可复制 + 标点误报清零

三个都是用户在实机上反馈的，逐个先复现再修。

### 问题 1：小窗年龄显示「62岁岁」

PACS 界面上年龄字段本来写作「年龄：62岁」，OCR 原样取回 `age = "62岁"`；
`mini_window._fill_patient()` 与 `fields.ReportFields.summary()` 都无条件拼

修法：新增 `reportqc/pacs/fields.py::format_demo(gender, age)`，先
`re.sub(r"[岁\s]+$", "", age)` 去掉尾部「岁」和空格再拼，两处共用：

```python
def format_demo(gender, age):
    g = (gender or "").strip() or "?"
    a = re.sub(r"[岁\s]+$", "", (age or "").strip())
    if not a:
        return "%s / ?" % g
    return "%s / %s岁" % (g, a)
```

### 问题 3：「标点符号异常」几乎每份报告都报

复现（`.ocr_tmp/t_punct.py`）后确认是**规则本身错**，不是 OCR 问题。
`checker_grammar.py` 原三条：

| 原规则 | 实测结果 |
|--------|----------|
| `[，,][。！？]` 标点连续使用 | 不同类型标点相邻，几乎全是 OCR 抖动，判不出真错 |
| `[汉字]{5,}[^一长串白名单]` 异常标点 | **白名单漏了半角 `, . ( ) : ;` 和省略号 `…`** → 真实报告每条都中 |
| `[，。！？、；：]{2,}` 重复标点 | 两个句号就报，OCR 抖一下就一条 |

根因：医生本来就习惯半角标点，OCR 也常把「，」认成「,」；白名单是
「枚举合法字符」的反查思路，永远补不完 —— 与 v1.17.0 缩写误报同一个坑。

改成**举证式**（只有正文里根本不该出现的字符才报）：

```python
self.punctuation_errors = [
    # 控制字符 / Unicode 替换符 / 私用区：OCR 失败或编码错误的铁证
    (r'[\x00-\x08\x0b\x0c\x0e-\x1f\ufffd\ue000-\uf8ff]', '异常字符', 'high'),
    # 编程符号混进正文（@ # $ ^ | \ ` 在影像报告里不可能出现）
    (r'[\u4e00-\u9fff][@#$^|\\`]', '异常符号', 'low'),
    # 同类标点连续 3 个以上（`，，` 两个多半是 OCR 抖动，不算错）
    (r'([，、；：])\1{2,}', '重复标点', 'low'),
]
```

`_check_punctuation()` 同时从 `findall` 改成 `finditer`：重复标点那条带捕获组，
`findall` 只返回组内容（丢掉实际连了几个标点）。描述文案也具体化
（「混入不该出现在报告里的符号「@」」），便于详情窗定位。

### 验收

| 用例 | 结果 |
|------|------|
| 半角逗号 / 半角括号+句点 / 半角冒号 | 零告警（原来 2 条/份） |

## v1.20.0：同时支持两套写报告界面

### 为什么要改

医生的机器上装了两套写报告软件，界面完全不一样：

.. code-block:: text

    ① 体检登记界面（本次新支持）        ② 标准 PACS 报告界面（原本已支持）
    ┌──────────────┬──────────────┐     ┌──────────────────────────────┐
    │ 项目编号 项目名称 检查结果  │     │ 姓名 性别 年龄 / 检查号 影像号 │
    ├──────────────┼──────────────┤     ├──────────────────────────────┤
    │ 08008 X光颈椎 │ 检查结果:    │     │ 影像所见                     │
    │  …椎体未见…  │ 1.颈椎生理…  │     │  ……                          │
    │ 08011 X光腰椎 │ 2.腰椎平片…  │     │ 诊断结果                     │
    │  …椎体未见…  │ 诊断建议:    │     │  ……                          │
    └──────────────┴──────────────┘     └──────────────────────────────┘

原来程序只有「一套区域 + 一套版式」，第二张图能识别，第一张图只能取到
患者信息 —— 正文里的「影像所见」标题不存在，`_split_body()` 找不到切分点。
用户的要求是「框选区域要能同时对这两个软件支持」。

### 改法：区域按窗口绑定 + 版式自适应

| 层次 | 改动 |
|------|------|
| 区域存储 | 单条 `x,y,w,h` → **配置数组**（JSON），每条带 `exe` / `title` / `rect` / `layout` / `name` |
| 区域选择 | 新增 `windowinfo.ForegroundWatcher`，1s 轮询记录「最近一个不属于本进程的前台窗口」；刷新时按 `exe` 匹配 |
| 正文切分 | `fields.detect_layout()` 判 `form` / `titled`，各走一套切分逻辑 |
| 标签表 | 补「体检编号」「体检号」「登记号」；中文标签按 `\s*` 允许字间空格 |
| 清理入口 | 设置窗「常规」页加「识别区域：N 个软件 … [清除]」 |

### 关键实现 1：为什么不能「刷新时现取前台窗口」

用户是点**悬浮小窗的按钮**触发刷新的。点击那一刻，前台窗口就是小窗自己，
现取必然拿到 `pythonw.exe`，两套区域都匹配不上。所以必须**持续记录**：

```python
class ForegroundWatcher(object):
    """记住「最近一个不是本进程的前台窗口」。"""
    def poll(self):
        exe, title = foreground()
        if self._self and exe == self._self:
            return                       # 就是本程序（用户点了小窗/主窗）
        self._exe, self._title = exe, title
```

主程序用 `QTimer(1000ms)` 驱动 `poll()`。开销是两个 Win32 调用，可忽略。

实现走 `user32.GetForegroundWindow` + `psapi.GetModuleBaseNameW`，全部 XP 起
可用，不依赖 shcore/DWM —— Win7 目标机必须守住这条线。

### 关键实现 2：为什么用 exe 做主键而不是窗口标题

PACS 窗口标题带患者姓名和检查号（「报告编辑 - 胡廷学」），换个病人标题就变。
拿标题当键，第二份报告就匹配不上。`exe` 才是稳定的。

`title` 只做兜底，且只在「两边 exe 都探测不到」时才比。另外**只剩一套配置时
无条件用它** —— 单软件用户（绝大多数）不该因为进程探测失败就退化成「未设置区域」。

### 关键实现 3：版式二的正文怎么切

`merge_lines()` 原来只输出拼接后的整行文本。版式二里，左侧项目表格与右侧
「检查结果」框**处在同一水平线**（y 差 3px 以内），必然被并成一行：

.. code-block:: text

    y≈185  [08008] [X光颈椎正侧位检] [颈椎生理曲度变直，诸颈椎椎体…] [1. 颈椎生理曲度变直。]
            └── 项目编号 ──┘└─ 项目名称 ─┘└───── 检查结果列 ─────┘└──── 右栏 ────┘

按整行归栏会一锅端。所以 `merge_lines()` 新增 `segs` 键，保留**每个分段自己的 x**：

```python
out.append({
    "y": ..., "x": ..., "h": ..., "text": "  ".join(...),
    "segs": [(t[1], t[3]) for t in row],   # [(x, text)]，按 x 升序
})
```

然后从列标题行反推三条竖线（项目编号 / 检查结果 / 右栏起点），逐段归栏：

```python
for x, t in row["segs"]:
    if x >= right_x - tol:      right_lines.append(t)   # 右栏
    elif x >= result_x - tol:   table_lines.append(t)   # 表格检查结果列
    elif _looks_like_table_body(t): table_lines.append(t)  # 见踩坑 1
```

右栏再以「诊断建议」为分界：之前全归所见，之后全归结论。三块正文**全部**参与质控。

### 踩坑

## v1.22.1：换皮肤后「按类型着色」失效

### 现象

患者列表的患者名本来按检查类型着色（CT 蓝 / DR 绿 / MR 紫 / 混合橙），
v1.21.0 上了皮肤系统后整列变成同一个颜色，功能看起来像被删掉了。

### 根因：QSS 的 `::item { color }` 会盖掉 ForegroundRole

v1.21.0 的全局样式表里给列表写了一条

```css
QTreeWidget::item { border-radius: 4px; color: <text>; }
```

**只要 QSS 给 `::item` 指定了 `color`，`QStyleSheetStyle` 就会在绘制条目时
用这个颜色覆盖 `QTreeWidgetItem::setForeground()` 设的 `ForegroundRole`。**
代码层面完全看不出来：`item.foreground(0).color()` 仍是 `#5ac88c`，
但画出来的像素是灰的。

实测取证（`_tools/probe_item_foreground.py`）：同一个纯红条目，
带 `::item { color }` 时渲染图里**一个红色像素都没有**，去掉后立即出现 `(247,27,30)`。

受害的不止患者列表，凡是靠 `setForeground` 表达语义的地方全部变灰：

| 位置 | 原本表达的意思 |
|------|----------------|
| `main.py` 患者树 | 检查类型（CT/DR/MR/混合） |
| `reportqc/ui/history_dialog.py` | 结论等级（红/橙/黄/绿） |
| `reportqc/ui/settings_dialog.py` | 置灰的不可用条目 |

### 修法

1. `theme.py`：`::item` 里**只留 `border-radius`，不写 `color`**。
   文字基色由 `QTreeView { color: ... }` 提供（进 palette），
   条目没设 ForegroundRole 时照样是正确颜色。`:selected` / `:hover` 保留
   `color` —— 那是整行统一配色，本来就该盖住条目前景色。
2. `main.py`：删掉「年龄缺失就把整行刷成 `text_muted`」的分支。
   标题里已经写着「年龄未知」，颜色应只表达检查类型。
3. 模态配色按皮肤分两套：浅色皮肤（ivory / celadon 列表底色是纯白）用
   同色相压暗版，否则原亮色对白底对比度只有 1.8~2.5（正文可读线是 4.5）。

| 类型 | 深色皮肤（对 #101216） | 浅色皮肤（对 #FFFFFF） |
|------|------------------------|------------------------|
| CT | `#58a6ff`（7.4） | `#2476ce`（4.6） |
| DR | `#5ac88c`（9.0） | `#188649`（4.6） |
| MR | `#ba8cff`（7.4） | `#812dff`（5.6） |
| 混合 | `#ffb050`（10.3） | `#a6661d`（4.6） |

### 验证

- `_tools/probe_item_foreground.py`：像素级证明 QSS 压制关系（改前红像素 0 个）
- `_tools/shot_patient_tree.py`：逐行取「该行最饱和像素」，与期望色**逐个比对**；
  四套皮肤下 13 个可见行全部精确命中（`#ba8cff` / `#58a6ff` / `#5ac88c` 等），
  修复前同一测法统计到 13731 个灰白像素、彩色 0 个
- 颜色选择也用脚本量化：保持 HSV 色相不变、逐级压暗到对比度 ≥ 4.6，
  再校验两两色距（最小 128）
- `_release_selfcheck.py` 117 → **124 项**：`::item` 不得写 `color`（先剥注释）、
  配色表齐全、两两色距 ≥ 60、填充逻辑里不得出现 `text_muted`、
  浅色皮肤专用配色存在、各皮肤对比度 ≥ 4.5

## v1.22.0：在线升级与增量补丁

### 为什么做

发行包 1.4 GB，客户机每次升级都要整包拷贝。实测这个包 **95% 从不变化**：

| 部分 | 体积 | 变化频率 |
|---|---|---|
| `pyenv\` 嵌入式 Python + 依赖 | 888 MB | 几乎不变（只有换依赖才变） |
| `xray\app\models\` ONNX 模型 | 441 MB | 只有换模型才变 |
| 全部 `.py` / `.md` / `.bat` | **3.7 MB** | 每次都变 |

真实数据：改 5 个文件（够大了吧，含 700 KB 的 main.py）→ 变更量 1.0 MB →
压缩后补丁 **348 KB**，是整包的 0.025%。

### 三层结构

```
_tools\make_patch.py          开发机：比对两版目录，产出补丁 zip
_tools\publish_update.py      开发机：签名索引 + 上传到服务器
        │
        ▼  HTTP（明文，靠签名保证完整性）
        │
updater.py                    客户机：拉索引 → 验签 → 逐级下载 → 校验 SHA256 → 解压
update_ui.py                  客户机：线程 + 更新窗口 + 启动静默检查
apply_patch.py                客户机：真正落地的执行器（补丁包内自带，离线也能用）
```

**关键取舍：`updater.py` 不 import PyQt5。** 它能脱离界面单独跑
（`python updater.py <url> <版本>` 直接打印升级计划），
所以整条网络与校验链路可以在无 GUI 的测试里覆盖。

### 服务端协议

`http://<host>/latest.json` + `latest.json.sig`，两个文件分开是刻意的：
签名针对 **latest.json 的原始字节**，客户端不需要重新序列化再比对 ——
省掉「JSON 规范形式不一致导致验签失败」这一整类疑难杂症。

```json
{
 "format": 1, "channel": "stable", "latest": "v1.22.0",
 "generated": "2026-10-30 18:00:00", "notes": "更新说明",
 "patches": {
   "v1.21.0": {"to":"v1.22.0","file":"patches/patch_v1.21.0_to_v1.22.0.zip",
               "size":356123,"sha256":"...","published":"..."}
 }
}
```

nginx 把 `/latest.json` 设成 `no-store`（否则客户机永远看到旧的索引），
`/patches/` 短缓存 600 秒；`autoindex off`、根路径 404，不暴露文件列表。

### 安全：为什么明文 HTTP 也敢用

升级包是**可执行代码**（`.py`），一旦被链路劫持就等于远程代码执行。
所以两道锁：

1. **索引 RSA-2048 签名**（PKCS#1 v1.5 + SHA256）。私钥只在开发机
   `_releases\keys\`，公钥硬编码在 `updater.py`；签名对不上直接中止，
   **绝不降级使用**。
2. **补丁包 SHA256**。索引可信之后，包内容按索引里的指纹逐个校验。

🔴 **验签不依赖 `cryptography`**。Win7 上这个库会因为 PATH 里另一份
libcrypto 崩溃（本机 Git Bash 里实测 exit 139 段错误）。
客户端验证只需要 `pow()` + `hashlib`：

```python
m = pow(int.from_bytes(sig,'big'), e, n)
em = m.to_bytes(k,'big')          # 期望 00 01 FF..FF 00 || DigestInfo(SHA256)
```

发布端签名用 `openssl dgst -sha256 -sign`（Git for Windows 自带），
两边都不引入任何 Python 第三方依赖。

> 顺带一提：`reportqc\config\report_qc.db` 这类业务库必须排除在补丁之外。
> 第一版排除规则只写了 `xray\app\data\*.db`，差点把质控记录覆盖掉；
> 现在规则是「除 pyenv 外任何 `.db` 一律不动」，新增业务库不用再改配置。

### 补丁链

客户机 v1.20.0、服务器最新 v1.22.0，且只有 1.21→1.22 一个包时，
`plan_update()` 会明确报错「请联系技术支持要全量安装包」，而不是装成半成品。

链条存在时（1.20→1.21、1.21→1.22），会**依次下载全部补丁**再一次性安装，
用户只重启一次。逐级应用天然满足「后一级的前置指纹 = 前一级的结果」。

### 安装与回滚

在线升级不重写安装逻辑，直接复用补丁包里的 `apply_patch.py`：

1. `stage_patch()` 解压到 `<软件目录>\_patch\`（顺带过滤 `../` 路径穿越）；
2. `update_ui.install_and_restart()` 用 `CT3D_QUIET=1` 启动
   `pyenv\python.exe _patch\apply_patch.py --target <软件目录> --source <_patch> --relaunch`，
   然后主程序 `QApplication.quit()`；
3. 安装器装完用 `pythonw.exe main.py` 把软件拉起来。

安装器本身的保障见「增量升级说明.md」：逐文件指纹校验、备份到
`_upgrade_backup\`、原子替换、失败逆序回滚。

⚠️ v1.22.3 之前这里有两个坑，症状是「点升级后软件关掉了、没再打开，手动打开还是老版本」：

- **不再经 `cmd /c 升级.bat` 中转**。路径含空格或中文时 cmd 会把参数拆坏，
  整次升级静默不执行。`升级.bat` 只留给现场手动双击用。
- **`timeout /t 3` 等不住**。主程序收到退出指令后，Python 释放 `main.py` / pyc
  句柄可能要更久，安装器这时覆盖会 `PermissionError` → 整体回滚。改为
  `replace_with_retry()` 重试替换，最多 45 秒。
- **失败必须可见且能自愈**：全过程写 `<软件目录>\_update_log.txt`；失败弹
  `MessageBoxW` 说明原因与备份路径；`--relaunch` 时**成败都会重启软件**
  （旧实现只在成功路径重启，失败时用户面对的是「程序自己消失了」）。
- 指纹不一致默认**备份后覆盖**（原件都在 `_upgrade_backup\`，可回滚），
  只有显式 `--strict` 才沿用「中止」的老行为 —— 客户机是终端用户，
  因为一处文档被改过就整包不升、还不给提示，代价远大于收益。

⚠️ v1.22.4 之前还有一个更隐蔽的坑，症状是「升级报『补丁包不完整：缺 manifest.json』」：

- `升级.bat` 里 `set "HERE=%~dp0"` 末尾带反斜杠，于是
  `--source "%HERE%"` 展开成 `--source "D:\x\_patch\"`。Windows CRT 把结尾的
  `\"` 当成**转义引号**，参数值实际变成 `D:\x\_patch"`（末尾多一个引号），
  拼出来的 `manifest.json` 路径不存在 → 一个文件都没装就退出。
  上面「不再经 bat 中转」只覆盖了新版客户机，**还停在旧版的客户机仍走 bat**，
  所以这个坑必须单独修。
- 修法有三层：`升级.bat` **不再传 `--source`**（执行器默认就用自己所在目录）；
  `apply_patch.resolve_source()` 对传入值做一次规整（去尾部引号 / 反斜杠 / `.`），
  该目录里没有 manifest 时退回脚本所在目录；`make_patch.py`
  生成 bat 时设护栏，出现 `--source "%HERE%"` 直接报错拒绝打包。
- 排查提示：这类「参数被引号吃掉」的问题在本地调 Python 时**复现不出来**
  （list 传参会自动转义），必须用 `subprocess.Popen(命令行字符串)` 才能忠实
  复刻 bat 的行为。

### 界面

「更新」按钮挂在右侧「工具区」标题行，和皮肤切换器并排（`tonal` 角色），
最小宽度 62px 避免文案从「更新」变「● 更新」时布局跳动。

## v1.21.0：四套界面皮肤（theme.py）

### 需求与约束

用户要求：「加一套精美的 UI 皮肤，**布局不变**，只改 UI 与配色，**一键切换**，
风格简洁、耐看、专业、精致」。

翻译成工程约束就是四条：

1. **不能碰布局** —— 所有尺寸、边距、控件层级保持原样，只改颜色与少量自绘；
2. **运行时切换** —— 点一下立刻生效，不重启、不重建主窗口（否则丢当前阅片状态）；
3. **一套代码撑多套皮肤** —— 不能出现 `if skin == "ivory": color = ...` 这种分叉；
4. **零外部资源** —— 发行包是绿色包（Win7 可用），不加图标/图片/字体文件。

### 整体结构

::

    theme.py
      ├── SKINS            4 套皮肤的语义 token（唯一数据源）
      ├── tokens()         派生色：accent_soft / sel_bg / well / control_line …
      ├── palette()        QPalette：让 QStyle 自己画的部分（禁用色、选中色）跟随
      ├── _QSS             全局样式表（%(token)s 模板，一套模板吃四套皮肤）
      ├── qss_*()          控件级工厂（阅片浮动条 / 缩略图条 / 拖放提示 …）
      ├── _SkinStyle        QProxyStyle 自绘勾选框、单选框、下拉箭头、数字箭头
      ├── apply/switch     灌进 QApplication
      ├── bind/role        控件级接线（弱引用登记，切皮肤时重建 QSS）
      └── SkinSwitcher     右侧「工具区」旁的按钮 + 自绘色卡浮层

关键点：**控件不认识皮肤，只认识 token**。一套皮肤 = 一组 token 值，
换皮肤 = 换一组值重跑同一套模板，所以不存在「某套皮肤漏改了某个控件」。

### token 口径

| token | 含义 |
|-------|------|
| `canvas` | 窗口底色（最底层） |
| `panel` | 侧栏 / 分组 / 卡片面 |
| `field` | 列表、输入框、文本域等「内容面」 |
| `raised` | 菜单、气泡、滑块等「浮起」面 |
| `button` / `button_hover` / `button_press` | 按钮三态 |
| `border` / `border_strong` | 分隔线 / 可交互元素描边 |
| `text` / `text_dim` / `text_muted` | 三级文字 |
| `accent` / `accent_hover` / `accent_press` | 唯一强调色（选中、主操作） |
| `accent_view` | **阅片区**专用强调色（要压在纯黑影像上，比 accent 亮） |
| `accent_alt` | 与 accent 相邻的第二色，只给加载动画双色环用 |
| `on_accent` | 强调色上的文字色（浅色皮肤也要够对比） |
| `danger` / `warning` / `success` | 语义状态色（浅色皮肤用深一档） |

派生色（`tokens()` 里算，不写死在皮肤里）：`accent_soft` / `accent_line` /
`danger_soft` / `sel_bg` / `sel_fg` / `scroll` / `scroll_hover` / `track` /
`shadow` / `control_line` / `well`。

四套皮肤：**石墨**（炭灰，默认）、**墨蓝**（海军蓝）、**象牙**（暖白纸感）、
**青瓷**（冷白釉）。

### 控件接线：三种情况三种办法

| 情况 | 办法 |
|------|------|
| 能用全局选择器解决的（按钮、输入框、列表、表头、滚动条…） | 只写进 `_QSS`，控件零改动 |
| 需要**语义**而不是颜色的（提示文字、错误文字、主操作按钮） | `theme.role(widget, "muted"/"danger"/"primary"/"tonal"/"ghost"…)` |
| 样式里带**控件自身尺寸/字号**的（阅片浮动条、缩略图、四角叠加信息、层厚滑杆） | `theme.bind(widget, lambda: theme.qss_xxx(...))`，切皮肤时用当前 token 重建 |

`theme.bind` 内部用弱引用登记（`weakref.ref` + `getattr(inst, name)`），
否则切皮肤的回调表会一直持有已关闭的窗口，造成泄漏。

### 阅片区为什么恒定深色

影像背景如果跟着皮肤变亮，同一个窗宽窗位下的灰阶观感会变，医生对
「这个结节是不是比以前亮」的直觉会被破坏。所以：

* `theme.VIEWER` 是一组**与皮肤无关**的常量（近黑底、玻璃 HUD、半透明遮罩）；
* 只有强调色跟着 `accent_view` 走（工具条选中态、层厚滑杆、MPR 信息文字）；
* 浮在影像上的工具条一律「深色玻璃」，浅色皮肤下也保持 —— 它压的是黑影像，
  不是浅色面板。

### 踩过的坑（改皮肤前必读）

| 现象 | 原因 | 正解 |
|------|------|------|
| 勾选框只剩一个孤零零的对勾、没有方框 | 给 `QCheckBox::indicator` 写**任何**规则，Qt 就切成「QSS 绘制」模式，只画实心块不再画原生勾选框；而 Fusion 在深色 palette 下方框描边与底色同色 | 不写 `::indicator` 规则，改用 `QProxyStyle.drawPrimitive(PE_IndicatorCheckBox)` 自绘 |
| 下拉框箭头变灰方块 | 用 CSS 三角（`border-left: 4px solid transparent`）画箭头，Qt 把三角填成实心块 | 不写 `::drop-down`，靠 `padding-right` 让位 + `PE_IndicatorArrowDown` 自绘 |
| 数字框的上下箭头不见了 | 数字框用的是 `PE_IndicatorSpinUp/SpinDown`，和下拉框的 `PE_IndicatorArrowUp/Down` **不是同一套 element** | 两类都放进 `_ARROW_ELEMENTS` 一起接管 |
| 质控对话框里所有按钮都被刷成面板底色 | `self.setStyleSheet("background:...;")` 是**万能选择器**，优先级高于应用级样式表，把子控件一起染色 | 删掉对话框级万能样式；确实要染就写 `#objectName { ... }` 限定 |
| 浅色皮肤下进度条看不见轨道 | 白槽 + 白底 | 新增 `well` token（浅色皮肤比 canvas 再暗一档） |
| 浅色皮肤下勾选框方框太淡 | `border_strong` 在白底上几乎看不见 | 新增 `control_line` token（`text_muted` 与 `border_strong` 的 55% 混合） |
| 禁用按钮在深色皮肤上「消失成一个洞」 | 禁用态底色被刷成 `panel`，与面板同色 | 禁用态保留 `button` 面，只压暗文字与描边 |
| 滑块在浅色皮肤上是一颗黑疙瘩 | 滑块填充用了 `text`（浅色皮肤下接近黑） | 填充改 `raised`（浮起面）+ 强调色描边 |
| 切换浮层里的色片发虚 | 没有按 2x DPR 绘制 | `_chip_pixmap` 内部 `setDevicePixelRatio(2)` |

### 报告质控模块的接入方式（特例）

`reportqc/ui/*` 是独立子包，模块级写了 `C_BG = "#1e2022"` 这类常量并在
构造时拼进 QSS 字符串。改成皮肤色有两个特殊要求：

1. **不能每次绘制都去算** —— 所以不是函数，而是一个**惰性对象**：

::

    # reportqc/ui/skin.py
    C_BG = lazy_color("canvas", "#1e2022")

    class LazyColor(object):
        def value(self):   # 用到时才向 theme 取当前皮肤色
            return theme.token(self._token, "") or self._fallback
        def __str__(self):      # 拼进 "%s" 时自动取当前值
            return self.value()

2. **切换皮肤要能刷新已打开的窗口** —— 小窗 `MiniReportWindow` 增加了
   `_apply_skin()`：只重刷样式、不重建窗口（重建会丢掉当前患者的质控结论），
   构建后调一次 + `theme.on_change(self._apply_skin)` 再调一次。

语义状态色（`LEVEL_COLORS`：红 / 橙 / 黄 / 绿）**刻意不跟随皮肤** ——
它们表达的是结论等级，跨皮肤必须一致，跟着皮肤变会让人误判。

### 加载动画与 Toast

由 `loading_ui._hud()` 每帧现取 —— 切皮肤后下一帧就是新颜色。

## v1.22.2：质控小窗「患者信息被压住」的真正原因

用户反馈：小窗的患者信息会被下面的「部位 / 时间」行和按钮区压住，
有时还看到文字重复、错别字只显示一半。

### 三个叠在一起的问题

第一次修只改了文案和折行，真正的原因是**高度算错**，所以必须一层层拆：

| # | 现象 | 真因 |
|---|------|------|
| 1 | 第三行（部位/时间）折成两行，第二行压在列表上 | `_pt_exam.setWordWrap(True)`；卡片高度被 `setFixedHeight(sizeHint())` 锁死，折出来的第二行无处可去，直接画到卡片外面 |
| 2 | 列表区整块压住患者卡下半截 | 窗口高度**手算**：`30 + 卡片 + 6 + 42 + 列表 + 12`。而 `QScrollArea.sizeHint()` 与它的最小高度实测差 20px，手算结果比 `layout.minimumSize()` 小 → Qt 只能让列表区压在卡片上 |
| 3 | 性别年龄显示成「男 /…」、字顶被切一半 | 截断用的是「标签自己当前宽度」：截短 → `sizeHint` 变小 → 列更窄 → 再截短（反馈环）；另外中文在该字体下 `ascent+descent` 恰好等于字号，行高取等值就等于贴着字画 |

### 改法

```python
# 1) 高度不再手算，问布局要；下限取 layout.minimumSize()
root = self.layout()
root.activate()
want  = root.sizeHint().height()
min_h = root.minimumSize().height()
self.resize(self.W, max(min_h, max(188, min(max_h, want))))

# 2) 卡片与它的容器一起锁高，避免窗口到上限时被压回来
self._patient_card.setFixedHeight(card_h)
self._card_host.setFixedHeight(card_h + 6)
```

* 患者卡三行**全部单行**：`_apply_patient_text()` 用 `QFontMetrics.elidedText`
  按实际宽度截断，全文进 tooltip；第三行用 `ElideMiddle` 保住末尾的检查时间。
* 性别年龄先落地再算姓名宽度（打断反馈环），且列宽上限 = 卡片宽的 42%。
* 每行 `setMinimumHeight(fontMetrics().height() + 4~6)`，字不再贴边。
* 部位与项目去重：`_join_unique()` 丢掉被更长片段包含的片段
  （「CT」+「胸部」+「胸部CT平扫（薄层）」→ 只留最后一条）。
* 第三行字号 10px → 11px、颜色亮一档：10px 宋体的竖钩会糊掉，看起来像「字被切了」。
* 底栏按六个按钮实际需要的宽度兜底最小窗宽，窄窗时按钮不互相压字。

## v1.23.0：升级服务器地址可配（换主机不用重装）

### 需求

升级服务器原来是代码常量 `updater.DEFAULT_BASE_URL`。换 IP / 换机房 / 内网自建镜像，
都只能改代码再发一版，而客户机连的恰恰是"旧地址已经不通"这条路 —— 死锁。

### 方案

地址加到 `app_settings.json`（软件目录，与「患者扫描目录」同文件）：

```json
{ "scan_dirs": ["D:/data"], "update_base_url": "http://10.0.0.8:8000" }
```

- 存**空串**表示跟随内置 `DEFAULT_BASE_URL` —— 这样以后代码里换默认地址，没动过这项的
  客户机会自动跟着变；存了具体地址才算"用户明确指定"。
- `app_settings.json` 在 `make_patch.py` 的 `EXCLUDE_NAMES` 里，**在线升级永不覆盖**，改一次长期有效。
- 为什么不用 QSettings：导出脱敏那个对话框用的是 QSettings（跟 Windows 用户走），但升级地址
  要跟**安装目录**走 —— 一台机器上装两份软件、或换 Windows 账户登录，都应该还是同一台服务器。

### 代码

* `updater.normalize_base_url(text)`：补 `http://`、去尾斜杠、去引号、去误粘的
  `/latest.json` 和 `?`/`#` 尾巴、协议名大小写不敏感；给不出可用主机就返回空串。
* `updater.read_app_settings(app_dir)` / `load_base_url(app_dir)`：读配置 + 回退默认。
  `resolve_base_url(dict)` 保留，内部改走 normalize。
  🔴 老实现要求输入**必须**以 `http://` 开头，否则静默丢弃回退默认 —— 现场最常见的
  「IP:端口」写法会被无声忽略，表现成「设置好像没生效」。
* `main.MainWindow._read_settings_config()` / `_write_settings_config(patch)`：
  **读-改-写**（临时文件 + `os.replace`）。
  🔴 原来是 `json.dump({"scan_dirs": ...})` 整体覆盖。同一个文件里多存一个键以后，
  改扫描目录会把升级地址冲掉，症状是「设置里明明改过，下次打开又变回默认」，且毫无报错。
* `main.SettingsDialog`：新增「在线升级服务器」分组 = 输入框 + 恢复默认 + **测试连接**。
  测试连接复用 `update_ui.CheckWorker`（拉索引 + 验签），`found`/`uptodate` 都算连通，
  `failed` 显示原因 —— 比 check_update 的"有没有新版本"更适合判断连通性。
  线程 `parent=None` 由对话框自己持有，`done()` 里 `wait(3000)`：否则关窗瞬间线程还在跑，
  QThread 包装对象析构 → `Destroyed while thread is still running` 硬崩。
  结果文字单独占一行、不设固定高度（`wordWrap` + 固定高度会画到容器外压住按钮）。
* `update_ui.UpdateDialog(..., base_url=None)`：默认 `updater.load_base_url(app_dir)`；
  检查失败时状态栏追加「服务器：<实际地址>」，换源后连错地方一眼看得出。

### 发布端

`_tools/sync_to_host.sh` 的 `BASE_URL` 改为从 `_tools/_server/server_config.json` 读
（与 `publish_update.py` 同一份配置）。原来脚本里写死一份、配置里写一份，换主机漏改
就会出现「补丁发到新主机了，脚本却去旧主机比对版本」→ 永远「版本没变，跳过」，零报错。

## v1.24.1：修「第五中节指骨未评级」+ 等级名统一

### 现象与真因

用户反馈部分片子提示「第五中节指骨未评级」。诊断脚本
（`_tools/boneage_diag_missing.py`、`_tools/boneage_conf_table.py`）在 9 张实测图上
复现：**13 个检测框一个不缺**，缺的是分类环节 —— `MIPFifth` 的分类置信度落在
0.17~0.29，被判「低于 0.30」直接 `continue`，不写进 `results_score`。

后果不是「少显示一行」，而是**该项按 0 分计入总分**：MIPFifth 满分 49/1000。
更典型的是 m17：该项判 12 档（满级，完全正确），置信度 0.24，照样被丢，白丢 49 分
—— 这是该片算出 15.35 岁（真 17）的原因之一。

### 为什么不能用全局阈值解决

MIP 是 13 项里最小、骨骺特征最弱的一项（第五指尤甚），模型 argmax 常对但
「不敢确信」。用同一个 0.30 卡，必然周期性丢项。而**放开全局阈值反而更差**：
实测 9 张（MAE）——

| 策略 | MAE | 平均已评关节 |
|---|---|---|
| A 全局 0.30（改前） | 0.60 | 12.0/13 |
| B MIP 放宽到 0.12 | **0.39** | 12.6/13 |
| C MIP/PIP/DIP 0.20 | 0.49 | 12.4/13 |
| D 全部保留（0.0） | 0.67 | 13.0/13 |
| E 全部 0.20 | 0.77 | 12.9/13 |

原因是桡骨（Radius）权重最高（满分 210），置信度低时 argmax 往往判错，
放开会把 1 分误差放大成 1 岁以上（g10 全部放开后 9.04 → 11.08，真值 10）。
所以只能**按模型分档**：`CLS_CONF_BY_MODEL`，MIP=0.10，其余 0.30。

  * 新增 `CLS_CONF_BY_MODEL`：分档阈值表，附实测依据注释。
  * `_classify_joints(..., detail_out=None)`：分档阈值按**比例**生效
    （`cls_conf * 分档/0.30`），保证界面设置里可调的 `boneage_cls_conf` 不被绕过；
    低置信项**保留计分**并标 `low_confidence`；`detail_out` 逐关节记录

  * `detect()`：新增 `low_confidence_joints`、`ungraded_joints`、`classify_detail`。

### 顺带修掉的不一致（同一处显示链路的另一个坑）

同一关节在标注图上写「8级」、在文字报告里写「12级」。原因是两套命名：
`level` 是**内部细分档序号**（1~14），`GRADE_NAMES` 才是 RUS-CHN 等级名（1~8 级，
